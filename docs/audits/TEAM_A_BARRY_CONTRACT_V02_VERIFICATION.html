Evidence Before Architecture

An independent trace of Team B's Phase 0 fixes and an adversarial review of the Barry Intelligence Contract v0.2. The semantic foundation is sound. The evidence underneath it is not: the contract's flagship worked example describes a subsystem whose only producer is unreachable.

Recommendation

Revise to v0.3

The foundation holds. The hierarchy classifies ten of eleven traced examples, the four scopes classify every concept tested but one, and the separation of authority from confidence is the document's best and most defensible idea. Nothing found here justifies reopening Phase 0 or stopping Phase 2.

Two findings dominate everything else and are stated up front because they change what Phase 2 should be.

Finding 1 · The contract's model example does not run

v0.2 calls relationship warmth "the most complete intelligence implementation in the current system" and "the model to generalise." netlify/functions/inferRelationshipWarmth.js is the only writer of warmth_level, warmth_level_source, warmth_level_inference_reason and barry_warmth_suggestion anywhere in the repository. It is not imported by any module, not present in the client's set of invoked .netlify/functions/* endpoints, not scheduled in netlify.toml, and not called by another function. There is no UI editor for warmth either. Six consumers read the field — the guardrail, the server assembler, three prompt builders, and a sort comparator — and every one of them reads a value that nothing produces.

Finding 2 · Phase 0's onboarding search runs with no ICP

Step 3's search-companies call posts users/{uid}/companyProfile/current. Nothing in the OnboardingFlow path ever writes that document — analyze-website writes only to dashboards/{uid}.modules[recon], and it skips even that for a new user because dashboards/{uid} does not exist until Step 3 calls initializeDashboard. The answers just captured in Step 3 are not passed either. The search Phase 0 correctly wired up therefore executes against {}.

PART 1B

The idempotency guard

When the latch closes, relative to each awaited operation

searchTriggeredRef.current = true executes on the second line of the handler, synchronously, in the same microtask as the click — before every await and before the only validation that can reject the run:

const handleFinishQuestions = async () => {
  if (searchTriggeredRef.current) return;   // guard read
  searchTriggeredRef.current = true;        // ← LATCH CLOSES HERE

  const userId = getActiveUserId();         // sync
  if (!userId) return;                      // ← returns with the latch held

  await initializeDashboard(userId);        // await 1
  await updateDoc(...);                     // await 2
  await user.getIdToken();                  // await 3
  await getDoc(companyProfile/current);     // await 4
  await setDoc({ barryState: 'SEARCHING' });// await 5
  fetch('/.netlify/functions/search-companies')  // not awaited
  await onboarding.markStep(...);           // await 6
  setStep(4);
ScenarioVerdictWhy

The critical question: does the ref prevent a legitimate retry?

Yes. The latch is taken before the run is known to be performable, so a pre-search failure is unrecoverable without a reload.

getActiveUserId() returns _impersonationCache?.targetUserId ?? auth.currentUser?.uid ?? null (ImpersonationContext.jsx:32-34). It reads the Firebase SDK object directly, while ProtectedRoute gates on App-level React state fed by onAuthStateChanged. Those two diverge for as long as it takes React to commit — so auth.currentUser can be null while OnboardingFlow is still mounted: a revoked session, a sign-out in another tab under local persistence, a cleared session mid-flow. Step 3 holds four free-text questions, so the component sits mounted for minutes.

When it happens the latch is closed and nothing has been done — no dashboard write, no barryState, no search, no markStep, no setStep(4). The Continue button is inert for the rest of the mount. It has no disabled state and no spinner, so the user sees a live-looking button that does nothing, with no error. Before the guard existed, the second click would have worked.

This is wrong independent of how often that specific window is hit. A return that leaves a one-shot latch closed is a design error on its own terms, and it makes any validation added above the latch in future silently unrecoverable.

The smallest correction

Move the latch below the only validation that can reject the run. Idempotency is fully preserved: getActiveUserId() is synchronous, so there is still no await between the guard read and the latch write and two rapid clicks still cannot interleave. Nothing about onboarding is redesigned.

What does not fit, and the one correction that covers it

Three kinds of object resist the four levels, and two of them are the same kind:

  • Derived, durable objects — Match Score, strategy_stats, RECON confidence. Computed from intelligence, reusable across decisions, existing before any decision. "Actionable Intelligence" is defined by relevance to the current decision, which they do not have.
  • Meta-intelligence — RECON confidence again, and the 'ok' | 'not_found' | 'error' status both assemblers were deliberately hardened to return. That distinction is not bookkeeping: both files carry comments explaining that conflating "no memory" with "read failed" made Barry generate cold-prospect copy for a warm relationship. Knowing what he cannot see is intelligence Barry acts on, and the hierarchy has no place for it.
  • Declared intent — engagement objective, mission goal. Enters at level 2 with no level-1 data.

Keep the four levels. Name Derived Intelligence explicitly as a kind that occupies level 2, and state that actionable is a relation between an intelligence object and a decision rather than a level an object sits in. That covers the first two cases and costs a paragraph.

Network and path intelligence — the specific stress test

"Sarah knows James who can introduce me to Acme." Decomposed against the repository:

  me ──────────────▶ Sarah     Relationship edge, user is one endpoint.       fits
  me ──────────────▶ James     Relationship edge, user is one endpoint.       fits
  Sarah ───────────▶ James     users/{uid}/referrals/{id}                    ← no primary subject
                              from_contact_id: sarah
                              to_contact_id:   james
  James ───────────▶ Acme      entity affiliation on James's record          fits

v0.2's rule is that every intelligence object has one primary subject, with related intelligence composed at decision time. Applied to the referral record the question is: what is its one primary subject? Under the current model the only available answer is "Relationship, scoped to one of the two contacts" — which is arbitrary. And the codebase has already refused to make that choice: the record lives in a separate top-level referrals collection keyed by neither contact (referralIntelligenceService.js:107, 208), with a copy denormalised onto both as contact.referral_data.

"One primary scope, composed at decision time" is not adequate here — but the fix is not a fifth scope.

Composition at decision time cannot conjure an edge that was never stored with a defined subject, and there is no non-arbitrary primary scope to pick. What is actually wrong is narrower: v0.2 already splits Relationship into Entity and Edge, and then silently assumes one endpoint of every edge is the user. Drop that assumption. An edge is subject-identified by an ordered pair, in which the user is a common but not mandatory endpoint.

The scope stays Relationship. What changes is that "one primary subject" means "one subject — which for an edge is a pair." Referrals, introductions and multi-hop paths become first-class in one sentence.

This is not speculative future-proofing. detectReferralOpportunities and detectLinkedInOpportunities already perform read-time graph inference, deriveIntroNbs already emits intro_offer next steps, and barryMissionChat already tells Barry to surface intro paths. The capability is half-built and the model does not describe it. This is the single most important conceptual correction in this review, and it is also the smallest.

Requiredness: intrinsic to the object, or computed at decision time?

v0.2 already concedes the answer and then contradicts it.

Dimension 12 says "Requiredness is always relative to an objective, not absolute." Section 5 says every intelligence object must express all thirteen dimensions. Those two statements cannot both hold.

The repository settles it. generate-engagement-message builds its target-market block only if (section3?.status === 'completed' && section3?.data) and proceeds perfectly well without it. barryGuardrail needs warmth_level only when the action is cold outreach. search-companies requires companyProfile.industries and nothing else. The same fact is required for one decision and irrelevant to the next, inside the same session.

Requiredness is not a dimension of intelligence. It is an input requirement of a decision. It belongs on the decision side, expressed as: this decision requires these intelligence categories, at this minimum status and confidence. Leaving it on the object guarantees it is stamped once, from the perspective of whichever decision the author had in mind, and is then wrong for every other consumer.

Consumer / Decision Class: the same argument, stronger

v0.2's justification for dimension 9 is diagnostic — "if nothing reads it now, what class of decisions would it inform?" That is a genuinely valuable question, and it is exactly how this review found eight dead stores. But the answer is a fact about the system's wiring, not about the intelligence object. If the server assembler starts reading relationship_context tomorrow, no intelligence object changed — the assembler changed.

Decisions should declare what they consume. Coverage is then computed, not maintained.

"Which categories have no consumer" becomes a query over a decision registry rather than a field maintained on thousands of objects. Stamping it per object guarantees drift — and the proof is in the contract itself, whose own claims about which fields have readers are wrong in four places. A field that documents wiring will always lag the wiring.

Three dimensions that are missing

  • Sensitivity / shareability. v0.2 states that Workspace intelligence "should eventually be shared across all users of the same organization," and then says nothing about which intelligence may cross that boundary. A contact's personal disclosure inside a Gmail thread is Relationship-scoped and must never become workspace-visible. With sharing named as a goal, this is not deferrable.
  • Subject stability. Every Relationship-scoped object depends on contactIdentityService resolving a person. When two contact records merge, what happens to their edges, memory and referral records? The contract has Superseded for values and nothing for subjects.
  • Cardinality. Is industries one object with a list value, or N objects? It decides whether "the user removed healthcare" is an overwrite or a retirement — that is, whether dimensions 11 and 13 can be applied at all. The worked examples silently assume both.

The three-concept separation is correct. Keep it.

Authority as precedence and confidence as evidential support are genuinely different, every example above demonstrates it, and this is the most valuable idea in v0.2 — subject only to the correction that authority belongs to the source rather than the object.

The lifecycle contains a contradiction

Unknown / Inferred / Confirmed / Observed / Contested / Stale / Superseded / Archived are not eight values of one variable. They are three variables wearing one label:

  How the current value was established   Unknown · Inferred · Confirmed · Observed
                                          — this is dimension 3, Source

  Whether it is still trustworthy        Stale
                                          — derived from dimension 7 + elapsed time

  Whether it is still the operative one  Superseded · Archived · (Contested)
                                          — the only genuine lifecycle states

v0.2 defines Source as "user assertion, website extraction, Gmail analysis, Apollo enrichment, Barry inference from behavior, outcome attribution, AI analysis." Inferred and Observed are two entries from that same list. Confirmed is a source event. Dimension 13 duplicates dimension 3 inside itself.

Does Observed belong in the same state machine as Confirmed, Stale and Contested?

No. It describes source and evidence type, not lifecycle position — and the contract's own text proves it twice.

One. The transition table contains Observed → updated value. That is not a transition between states; it is "new evidence arrived and the value changed." Every other row moves between two states. Observed has no outgoing transition to another status because it is not a status.

Two. The Status-vs-Confidence table reads Observed | High | Validated through real outcomes — strongest evidential basis. That sentence defines an evidence tier. The same objection applies to Inferred.

And from the codebase. warmth_level_source: 'barry_inferred' | 'user_set' is a source field. The contract's Example A maps barry_inferred to status Inferred and user_set to status Confirmed — reading one stored value as both dimension 3 and dimension 13. The collapse is visible inside the document's own worked example.

There is a second, independent problem: Contested is not mutually exclusive with the rest. A value can be Confirmed and Contested — that is precisely what barry_warmth_suggestion represents — and can be Stale and Contested. As a single-valued enum, moving to Contested erases how the value was established. That is a modelling error, not a naming quibble.

Per the brief this is returned rather than redesigned. Stated minimally, the correction is: Status carries operative status only — Active / Superseded / Archived — with Contested and Stale as orthogonal, derivable flags, and Unknown / Inferred / Confirmed / Observed relocated into Source as an evidence tier. Two dimensions change; nothing else moves.

Testing the architecture principle

"One intelligence contract does not mean one intelligence database" — agreed, and the repository supports it.

Storage really is appropriately distributed. Nothing found here argues for consolidating Firestore.

"Client-side for business breadth, server-side for relationship depth — no surface calls both" — false, and the correction changes the size of Phase 2.

At least three surfaces already combine business and relationship context: generate-engagement-message, barryMissionChat and barryFirstTouch. The problem is not that no surface calls both. It is that every surface assembles its own set and no two agree. RECON is extracted by four separate code paths with four different section sets and two truncation rules. Relationship memory lives in two mutually unaware stores. Priority is derived twice. Referral intelligence reaches no Barry surface at all while Barry is instructed to reason about it.

"The context assembly layer is the unification point" survives — it is still the right answer. What does not survive is the sizing. This is not one integration between two systems; it is a consolidation of nine.

PART 6

Recommendation

Verdict

Revise to v0.3

Not reopen. The foundation is sound. The hierarchy classifies ten of eleven traced examples. The four scopes classify every concept tested but one, and that one needs a clarification rather than a fifth scope. The authority/confidence separation is correct and well argued. All three governing rules are supported by repository evidence. Nothing here justifies stopping.

Not freeze. The document is anchored on a worked example that does not run, its status dimension is internally inconsistent, two of its thirteen dimensions belong to the consumer rather than the object, and nine of its supporting evidence claims are contradicted by the code — in a document that closes by guaranteeing every reference traces to a cited path. Freezing it fixes those into the foundation.

The six corrections

  • C1

    Correct the evidence, and re-anchor the model example

    Replace Example A's warmth trace with the finding that its only producer is unreachable, and re-anchor "the model to generalise" on a subsystem that runs — barry_memory + barryContextAssembler + recommendStrategy is the honest candidate. Fix warmth_reasons → warmth_level_inference_reason, relationship_state_source → warmth_level_source, what_worked → what_has_worked, engagement_timeline → timeline (and drop the "never consumed" claim), the enrichment_provenance claim, the section 1 / section 2 value-proposition mix-up, and "Scout swipes produce zero learning".

  • C2

    Move Requiredness and Consumer / Decision Class off the object

    Requiredness becomes a decision's input requirement — this decision needs these categories at this minimum status and confidence. Consumer becomes a decision registry, from which coverage and dead storage are computed. Eleven dimensions on the object, two on the decision. This is the correction with the largest downstream effect, because it determines the shape of whatever assembler Phase 3 builds.

  • C3

    Split dimension 13

    Move Unknown / Inferred / Confirmed / Observed into Source as an evidence tier. Leave Status as operative status only — Active / Superseded / Archived — with Contested and Stale as orthogonal, derivable flags rather than mutually exclusive enum members. As drafted, the enum duplicates dimension 3 and forbids states the product already produces.

  • C4

    Make Authority and Contradiction behavior source-level policy

    Both answer "which source wins," which is a property of the source pair and the category. Keeping them per-object reproduces the CANONICAL_FIELDS failure — protection with no explanation, which is exactly what the Evidence Rule forbids.

  • C5

    Let a Relationship edge have two endpoints

    The user is a common endpoint, not a mandatory one. This makes referrals, introductions and multi-hop paths first-class without a fifth scope, and it is already required by code that exists: users/{uid}/referrals, detectReferralOpportunities, deriveIntroNbs.

  • C6

    Name Derived Intelligence, and make "actionable" a relation

    Match Score, strategy_stats and RECON confidence are computed from intelligence, are durable, and precede any decision. Say that actionable describes a relation between an intelligence object and a decision rather than a level an object occupies. Without this, derived objects have no correct home.

Optional but cheap: add Sensitivity / shareability as a fourteenth dimension. v0.2 names cross-user workspace sharing as a goal; without it the first sharing feature will leak relationship-scoped disclosures.

What Phase 2 should be

Recommended · not implemented here

Phase 2 = Producer / Consumer Reconciliation. A read-only, evidence-first pass that produces the one artifact the contract explicitly defers and that every later phase depends on: a verified map of every intelligence producer, every store, every consumer, and every path between them.

Why this and not the unified assembler, and not #561: this review found, without looking for them, four write-only stores, three dead assemblers, one unreachable producer sitting beneath six live consumers, and nine mutually inconsistent assembly paths. An assembler built on that inventory would faithfully wire together fields that are already wrong. The contract's Consumer dimension is the diagnostic that finds them — and corrections C2 and C6 are what make it usable.

  1. A producer → store → consumer table for every category in the contract's Section 8, each row traced to a file and line and each verified reachable. The inferRelationshipWarmth class of error must not survive it.
  2. The dead-storage list with one decision per entry — wire it or delete it. Eight candidates are already identified in Part 4.
  3. The surface → required-categories table: dimensions 12 and 9 relocated per C2. This is the deferred "Context Requirements by Surface" item, and it is the specification the eventual assembler is written against.
  4. Reconciliation decisions for the multi-writer fields this review surfaced: value proposition (5 locations), target industries (6), engagement objective (4), companiesFoundCount (2 writers, no rule).

Phase 3 is then the unified assembly layer, written against item 3. Phase 4 is #561 — answerable by then, because Part 3's matrix establishes that only RECON section 3 has a claim on Match Score, and the reconciliation will have established which of the six target-industry stores is authoritative.
