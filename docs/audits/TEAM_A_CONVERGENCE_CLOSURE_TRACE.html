C1 — ICP projection lifecycle

Reachable flow, per bridge-only writer

All three follow the same shape: write the bridge, immediately search from it, never touch icpProfiles, never name an ICP. Their edits exist only in the bridge until some other path picks them up.

Q1 — Do bridge-only edits ever update an existing icpProfiles document?

Yes — through one reachable path, and it is none of the three writers above.

Five criteria fields are written into an existing profile document. The merge base is contextStack.icpProfile, resolved by barryContextStack.getActiveMessagingProfile:62: the active profile when one exists, otherwise the bridge, returned stamped id: DEFAULT_ICP_ID (:75).

So the three named writers do not themselves update a profile, but the bridge state they leave behind is the fallback merge base for this path.

Q2 — Can bridge-only edits create a new ICP identity?

Yes — two reachable paths, both gated on the same condition: zero existing icpProfiles documents.

  • ICPSettings:64 — guard if (icps.length === 0). Reads companyProfile/current, mints icp_${Date.now()}, seeds eleven fields from the bridge (industries, companySizes, revenueRanges, skipRevenue, locations, isNationwide, targetTitles, scoringWeights, foundedAgeRange, managedByBarry, lookalikeSeed), then setDoc.
  • dashboardUtils:281 — guard if (icpSnap.empty). Reads the bridge, creates icpProfiles/default with isActive: true, status: 'active'.

Exact condition in both cases: the icpProfiles collection must be empty. Once any profile exists, neither path can run, and bridge edits can no longer mint an identity.

Q3 — On activation, is the bridge overwritten with that profile's criteria?

Yes on two paths, and no on a third — the distinction matters.

  • setActiveIcpProfile:35 — batch.set(companyProfile/current, {...targetData, isActive: true, status: 'active'}). A full document overwrite, not a merge. Called by ICPSettings.handleSetActive:156.
  • dashboardUtils:343 — Step 4, batch.set(companyProfile/current, {...activeProfileData}). Also a full overwrite, inside the one-time migratedMultiICP branch.
  • DailyLeads.handleICPSwitch:1523 — writes nothing. It sets React state, re-filters allCompaniesRef and rescores in memory. No bridge write, no isActive write, no Firestore write of any kind.

The in-session ICP switcher in Daily Discoveries therefore leaves both the bridge and the persisted isActive flag pointing at the previously activated profile, while the user works under a different one.

Q4 — Is there a reachable path where one ICP's criteria are persisted under another ICP's identity?

Yes. Traced, every hop cited. The destination is always icpProfiles/default.

1  ICP A is active.
   setActiveIcpProfile:35 has mirrored A's criteria into companyProfile/current.

2  User deletes ICP A in ICP Settings.
   ICPSettings.handleDeleteICP:175  deleteDoc(icpProfiles/A)
   Guard is only `icpList.length <= 1`. No promotion of another profile,
    no isActive write, no bridge write.
   → Zero profiles now carry isActive:true, while ≥1 profile still exists.
   → The bridge still holds A's criteria.

3  User confirms an ICP change in the Barry dashboard chat.
   barryContextStack:70   active-profile query returns empty
   barryContextStack:75   falls back to the bridge, returns { id: DEFAULT_ICP_ID, ...A's criteria }
   BarryChatPanel:568     passes that as `existingProfile`
   updateIcpFromChat:63   icpSnap.empty → targetRef = icpProfiles/default
   updateIcpFromChat:78   setDoc(icpProfiles/default, { …A's criteria merged with the delta })

Result  Deleted ICP A's criteria are persisted under the default ICP's identity.

The enabling defect is step 2: handleDeleteICP permits deletion of the active profile without reassigning activity, which is the only reachable way to reach a state where profiles exist and none is active. Every downstream fallback in the chain then resolves to default, and none of them can tell that the criteria came from somewhere else.

Q5 — What happens to unsynchronized bridge-only edits after an ICP switch?

Classification — CONDITION-DEPENDENT

OVERWRITTEN when the switch goes through ICPSettings.handleSetActive:156 → setActiveIcpProfile:35. That call is batch.set, not a merge, so every bridge-only edit is discarded with no read-before-write and no warning.

PRESERVED — and orphaned when the switch goes through DailyLeads.handleICPSwitch:1523. Nothing is written, so the edits survive in the bridge while the user works under a different ICP in session. They remain the fallback merge base for updateIcpFromChat and the seed for the two bootstrap paths in Q2.

PROMOTED only in the Q2 condition — icpProfiles empty — where the bridge becomes a new profile wholesale.

The condition is which switching surface the user used. The two surfaces are not equivalent, and nothing reconciles them.

C3 — First-search targeting contract

buildApolloQuery (search-companies.js:659, called once at :289) emits at most four Apollo parameters. Everything else the profile carries is either applied after retrieval, logged, or ignored.

query = { page: 1, per_page: 50 }                          always
  + q_organization_keyword_tags          ← industries ∪ companyKeywords ∪ adaptiveSignals
  + organization_num_employees_ranges    ← companySizes, "51-100" → "51,100"
  + organization_locations               ← locations via `${state}, United States`
                                            or ["United States"] when isNationwide

Pairing it with one of the two structured filters is the smallest currently-supported combination that constrains retrieval on a bounded axis. isNationwide alone yields ["United States"] — a country-level bound that narrows very little.
Executable vs meaningfully ICP-targeted

Executable requires nothing. Class A is empty: {} reaches Apollo and returns results. The Phase 0B fields make the profile non-empty in dashboards/{userId} but leave the query byte-identical to the empty case, because they are stored somewhere search-companies never reads.

Meaningfully targeted requires industries at minimum, and one structured filter to bound it. Only three inputs reach Apollo as retrieval constraints — industries, companySizes, locations — and only two of those are structured. Revenue is commented out, exclusions have no parameter, titles and lookalike seed are unused, and the Apollo industry-ID mapper is dead.
