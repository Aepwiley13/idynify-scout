§3

Item 3 — the five Scout layers, reconciled

First, a naming collision worth settling before the model is frozen. Document 1 §2 already defines "The Five Layers" — and they are not these:

Barry OS five layers  (Document 1 §2 — a provenance taxonomy)
  Signal → Awareness → Recommendation → Prepared Action → Executed Action
  "These are not stages in a pipeline. They are distinct object types
   with distinct storage, distinct lifecycles, and distinct ownership."

Scout intelligence layers  (this model — a judgment stack)
  Eligibility → Match → Confidence → Priority → Relationship Intel → Next Action

These are orthogonal, not competing. Every Scout layer below lives inside one or two Barry OS layers. Eligibility, Match and Confidence are all Layer-2 facts about a company. Priority and Next Action are Layer-3 recommendations. Relationship Intelligence straddles both. Naming the Scout stack "the five layers" will collide with a frozen document — I recommend "the Scout judgment stack" or similar, and I have used that framing throughout.

Two contradictions inside the frozen stack that this model must not inherit

Documents 1–3 are frozen and Document 4 explicitly "may not redefine" them. It does anyway, in two places that bear directly on Match:

What the matrix proves

1 · Persistence destroys 80% of the score's discriminating power

Apollo's mixed_companies/search endpoint returns neither employee count nor headquarters location — the code says so in its own comments at search-companies.js:939 and :956. So the document written to Firestore carries name, industry, revenue, founded_year, phone, and three URLs. Two of the four scored dimensions are structurally absent from every company Scout has ever discovered.

Both resolve to UNKNOWN = 50 for every company, contributing a constant 2,000 of the 10,000-point weighted numerator regardless of what the company is. The consequence is scenario 1 versus scenario 2: on raw Apollo data a perfect company and an industry-only company are 50 points apart. On the document that actually ships they are 10 points apart — 80 versus 70. And scenario 2 is not an outlier: six of the twelve displayed scores land in the 70–80 band.

2 · Industry is fabricated when Apollo cannot classify a company

saveCompaniesToFirestore:960 resolves industry as:

const industry = company.industry
              || company.primary_industry
              || companyProfile.industries?.[0]   // ← the user's own ICP
              || 'Unknown';

When Apollo returns no industry, the company is stamped with the first industry from the user's ICP. It then scores a confirmed match on the 50-weight dimension, and generateMatchReasons renders the sentence "Matches your target industry: Financial Services." I ran it:

Apollo returnedStored asScoreReason shown to the user
no industryFinancial Services75"Matches your target industry: Financial Services"
Financial ServicesFinancial Services75"Matches your target industry: Financial Services"

Identical score. Identical explanation. In one of those rows IDYNIFY knows the company's industry; in the other it is reading back the user's own input and presenting it as a finding. This is the most serious defect in the report — not because the arithmetic is wrong, but because the explanation is false, and Law 11 of the Barry OS principles is "if Barry cannot explain why he recommended something, that recommendation should not ship."

3 · The literal string "Unknown" is scored as a definite miss

When the ICP has no industries either, the fallback lands on the literal 'Unknown'. evalIndustry treats it as a real value that matches nothing — match: 0, not UNKNOWN: 50:

Company documentScoreMeaning applied
industry: "Unknown"25Confirmed miss
industry field absent50Unknown data

A 25-point swing decided by which branch of a fallback chain fired, for two documents that encode the same fact: we do not know this company's industry.

4 · The server formula rewards having wrong data over having no data

Scenario 7 versus scenario 6, and the line that causes it (calculateFitScore:1328):

if (company.revenue_range) {
  score += 20;          // points for the field existing, not for matching
}

Scenario 7's revenue is $1B+ against an ICP wanting $10M-$20M. It scores the full 20. Scenario 6, which simply has no revenue data, scores 0. A company that is demonstrably wrong on a dimension outranks one that is merely unmeasured, by 20 points. This is the single strongest argument against reviving the server scorer as written.

5 · The server's weighting inverts the ICP's own priority

Scenario 10 — wrong industry, everything else correct — scores 70 on the server and is admitted. Scenario 2 — correct industry, everything else wrong — scores 50 and barely survives. The server weights industry at 30 of 100 while location and size together carry 50. The client weights industry at 50 alone. The client is right: industry is the axis an ICP is actually built on, and every user-facing string in Scout says so.

6 · Coverage is invisible in the number

Scenario 9 knows one of four dimensions and displays 75. Scenario 1 knows all four and every one matches, and displays 80. Five points separate near-total ignorance from near-total confirmation. There is no way for a user, or for any downstream consumer, to tell those two apart from the score. This is item 6's entire justification, in one row pair.

7 · Neither formula knows about avoid-industries

Scenario 11 scores identically to scenario 10. RECON §3 collects avoidIndustries ("Any industries that are bad fit?"). Nothing reads it — not the scorers, not the Apollo query builder. A user who explicitly told IDYNIFY to avoid Hospitality gets Hospitality companies at the same rank as any other industry miss. That is an Eligibility failure, not a Match failure, and it is the clearest case in the report of collected intelligence going nowhere.

§5

Item 5 — challenging the < 50 gate

The gate was to be scrutinised for doing two jobs: deciding whether Scout retains a company, and telling the user how well it fits. The scrutiny has an unexpected answer.

The < 50 gate does not run. It has not been coupling anything.

It lives in validateCompanyData (search-companies.js:1135), which no code path calls. Discovery admits every company Apollo returns, subject only to passesAgeFilter and deduplication.

But the coupling the question was aimed at is real — it just sits somewhere else, and it is worse.

The gate that is actually live

MissionControl.jsx:15 defines ICP_SCORE_THRESHOLD = 70 and applies it in five places to compute the serviceable market, the target list, and the map. It reads the persisted fit_score — and discovery never writes one. The only writer is recalculateAllScores in ICPSettings.jsx:274, which fires when a user saves their ICP.

Discovery writes company  ──▶  no fit_score field
DailyLeads reads it       ──▶  scores in memory, never persists
Mission Control reads it  ──▶  fit_score == null → excluded from SOM
User re-saves their ICP   ──▶  fit_score finally written for every company

So a company discovered today is invisible to Mission Control's market view until the user happens to open ICP Settings and press Save. Two surfaces show two different Match Scores for the same company, and the mechanism that reconciles them is a button in a settings page. That is a genuine coupling defect, it is live, and it is not the one the question named.

Should a low Match Score make a company disappear?

No. Match should rank; Eligibility should admit. The implications, taken in the order asked:

Recommendation — no code change requested

Do not revive the < 50 gate. The right disposition for the dead server scoring block is deletion, in its own PR, with the reasoning recorded — but that is a separate authorisation and I am not requesting it here.

Keep Eligibility and Match separate and keep them where they belong. Eligibility is a server-side, pre-write, binary admission decision — today passesAgeFilter and dedup, and the natural home for avoidIndustries. Match is a ranking signal computed against an ICP and never a reason to discard.

The live coupling worth fixing first is not a threshold at all — it is that Mission Control's ICP_SCORE_THRESHOLD = 70 reads a field discovery never writes. That is a real user-visible bug today: newly discovered companies are missing from the market view. It needs no new architecture to fix. See §9-H.

Item 6 — what Scout Confidence should mean

The two candidates, and why they are not the same thing:

Coverage confidenceEvidence confidence
Claim"We could evaluate 3 of the 4 dimensions your ICP configures.""The values we used are accurate and current."
Computed fromWhich dimensions resolved to real data rather than UNKNOWN. Pure arithmetic over what is in hand.Source authority, field age, corroboration across providers, verification history.

Both failure modes are real. Apollo can return all four dimensions — full coverage — while the employee count is from a two-year-old crawl. And a freshly verified single field is strong evidence about almost nothing.

Recommendation: coverage only, and not as a new field

Scout needs coverage confidence first, alone, and immediately. Three reasons, in order of weight:

  1. Coverage is the failure Scout actually has. §4 scenario 9 versus scenario 1: one known dimension displays 75, four known and matching displays 80. The problem in production is not that IDYNIFY's data is stale — it is that two of four dimensions do not exist on any company record. Coverage names exactly that. Evidence confidence would report "high" on all four scenarios and tell the user nothing.
  2. Evidence confidence is not computable today and would have to be invented. There is no provenance, no field-level timestamp, no second source to corroborate against, no verification history. Building it means either a new vendor dependency — explicitly out of scope — or a fabricated number, which is the exact class of defect §4 catalogues. A confidence score with no evidence behind it would be the most ironic possible outcome of this investigation.
  3. Coverage is honest at zero cost. evaluateDimensions already returns { active, match, unknown } for all four dimensions. The count of active && !unknown is coverage. It requires no schema change, no new write path, and no storage — it is derivable at read time from data already in hand.

That third point matters for the "no schema changes" guardrail: coverage does not need a field at all. It is a function of the company document and the ICP, exactly like the score itself, and can be returned alongside it from scoreCompany. The right first move is a derived value, not a stored one.

Two things coverage must get right that the current score gets wrong

  • Unconfigured is not unknown. Scenario 8 — a perfect match on an ICP that does not configure revenue — has full coverage of 3 of 3, not 3 of 4. calculateICPScore already normalises over active dimensions correctly; coverage must use the same denominator.
  • "Unknown" the string is unknown data. Today industry: "Unknown" scores as a confirmed miss (§4.3). Whatever consumes coverage must treat the literal fallback string as absence, or coverage will disagree with the score it accompanies.

Where evidence confidence goes

Not discarded — deferred, and it already has a home in the frozen contract. Doc 2's LearnedIntelligence carries confidence: 0.0–1.0 backed by data_points and supporting_signals, and Doc 2's Recommendation carries confidence: 0.0–1.0 beside a reasoning_trace. Both are evidence confidence, both are Barry-owned, and both belong to Priority and Next Action rather than to Match. When IDYNIFY has provenance, evidence confidence attaches there.

Naming

If both eventually exist, they must not share the word. I suggest Coverage for what Scout ships now — a count, expressed as "3 of 4 criteria assessed" — and reserve Confidence for the 0.0–1.0 evidence-backed figure the frozen contract already defines. Two numbers both called "confidence" on the same card would recreate the exact ambiguity this investigation exists to remove.

Dependency on the missing document.

The direction stated that Barry Intelligence Contract v0.2 "separates evidence, source, authority, confidence and temporal scope for exactly this reason." I could not read it. If v0.2 defines a specific coverage-versus-confidence split, this recommendation should be checked against it before anything is built.

Classification summary

  • DUPLICATE — 3 concepts (industries, company size, revenue). Same intelligence, asked twice, stored in incompatible bucket schemes. RECON's 11-50 straddles the ICP's 11-20 and 21-50; RECON's $5M-$20M straddles four ICP bands. These cannot be mechanically merged — a migration has to decide which vocabulary survives, and the answer is forced: the ICP's, because those values are fed to Apollo.
  • RELATED — 1 concept (growth stage / founded age). Correlated but genuinely different: a bootstrapped 20-year-old company and a Series C 3-year-old both exist, and age does not imply stage.
  • NOT ACTUALLY THE SAME — 3 concepts (geography, buyer titles, all of §4). Shared vocabulary, different semantics. Geography is the sharpest case: "Local (city/metro)" and a US state list are not the same kind of answer, and neither can be derived from the other.
  • MISSION OVERRIDE — 0 concepts. No temporary, mission-scoped targeting store exists. The nearest thing is icpProfiles multi-profile switching via isActive, and that is durable workspace intelligence, not a mission preference. This is worth stating plainly because it protects against a wrong consolidation: nothing in the current data model is a temporary override, so nothing would be destroyed by unifying the durable stores — but the multi-ICP isActive mechanism must survive any unification, because it is the hook a future mission-scoped override would hang from.
  • Unconsumed RECON intelligence — 6 fields (avoidIndustries, companyType, budgetRange, decisionSpeed, marketSize, growthStage). The user answered six required questions whose answers nothing reads.

  3. Section 3 is written twice. Once into the dashboard module via saveSectionData, and again to users/{uid}.section3Answers by the component itself. Only the first is read.
The answer to the reframed #561

There is no authoritative source of ICP intelligence today. There are four stores, three writers that bypass the one with a schema, and a drift detector that cannot run. This is not a case of two systems disagreeing about which should win — it is a case of no system having been designated.

The decision to make is narrow and it is not a consolidation: designate icpProfiles as authoritative, demote companyProfile/current to a true derived cache with a single writer, and treat RECON §3 as elicitation rather than storage — the interview that helps a user articulate an ICP, which then writes through to icpProfiles in the ICP's own vocabulary. RECON §4 stays exactly where it is and never touches Match.

swipedAt:            ISO timestamp
swipeDirection:      'right' | 'left'
swipedForICPId:      the active ICP at swipe time   (only when one is active)
barryFeedback:          optional free text — right swipes only
barryRejectionFeedback: optional free text — left swipes only

Plus two counters at scoutProgress/swipes and scoutProgress/streak. Note what is not written: no Match Score at swipe time, no coverage, no ICP snapshot, no dwell time, no card position, no reason code.

What currently consumes it

  • Saves → savedIndustries, derived from the current batch only, passed to search-companies as adaptiveSignals to bias the next Apollo query's industry keywords. Batch-scoped, never persisted.
  • Saves → the Barry nudge, which fires when 3 of the last 5 saves share an industry. Computed from sessionSavedCompanies — session state, discarded on reload.
  • Saves → auto people-discovery using targetTitles. Unrelated to learning.
  • Skips → nothing. A rejection sets a status and, if the user typed one, stores a sentence no code reads.

So Scout accumulates swipe events and consumes almost none of them. That is the honest starting position.

The frozen contract already rules on this

Two constraints from Document 2 bound anything built here, and both cut against fast learning:

  • A swipe is an evaluation result, not a lifecycle state. The Company object's field mapping reads: swipe_* → icp_decision (acceptance/rejection is an evaluation result, not a lifecycle state). A Save means "this company was judged a fit" — it does not mean the ICP changed.
  • Learned Intelligence forbids single-session writes. "Who may write: Statistical aggregation pipeline only. Never single-session writes — Learned Intelligence requires patterns observed across 3+ sessions, relationships, or missions." proposed → confirmed without 3+ data points is listed as an illegal transition, and there is a category named icp_correlation waiting for exactly this.

The current Barry nudge fires on 3 of the last 5 saves within one session. Under the frozen contract that is a legitimate observation to show the user, and an illegitimate basis for durable intelligence. It is currently used for the former, which is correct.

What this means

No single swipe supports any automatic change to Workspace ICP intelligence. The direction's own list of six possible meanings for a Save is the proof: the raw event is compatible with all six and distinguishes none. Aggregation across sessions raises confidence enough to propose, never enough to apply.

The most valuable observation in the table is not the one that would make Scout learn faster. It is the third row: a Save on a low-Match company is a labelled disagreement between the user and the model, and it is free to record. Given §4, where the score is computed over two structurally-absent dimensions and a sometimes-fabricated third, disagreement events are the only honest external check Scout currently has on its own arithmetic.

They cannot be recorded today, because the score that was displayed at swipe time is not persisted with the swipe. That is a one-field gap — and it is the cheapest thing on this list to close, though not the first thing to build (§9-H).

§9

Item 9 — the eight answers

  1. A · What exactly is Match?

    Match is the degree to which a company's observed firmographic attributes agree with the criteria the user has stated in their active ICP — and nothing else.

    It is not a prediction of whether the company will buy, not a measure of how interesting it is today, and not a statement about how much IDYNIFY knows. Those are Priority and Confidence.

  2. B · What exactly is Confidence?

    Confidence is how much of the ICP's own criteria IDYNIFY was actually able to evaluate when it computed Match — a count of assessed dimensions over configured dimensions, not a judgment about the data's quality.

    Ship this as Coverage. Reserve the word "Confidence" for the evidence-backed 0.0–1.0 figure the frozen contract already defines on Recommendation and Learned Intelligence (§6).

  3. C · What exactly is Eligibility?

    Eligibility is a binary, pre-write admission decision about whether a company may enter consideration at all — a rule, never a score, and never reversible by a good Match.

    Today it is passesAgeFilter and deduplication. avoidIndustries belongs here and is currently nowhere.

  4. D · Should Match gate the queue?

    NO.

    Three reasons, weighted by how much they survive being wrong about everything else:

    1. The score is not currently trustworthy enough to delete on. Two of four dimensions are structurally absent, the third is sometimes copied from the user's own ICP, and coverage is invisible in the number. A gate on this score removes the unmeasured, not the unfit — §4 scenario 9 is dropped while scenario 10, a confirmed industry miss, is kept.
    2. Gating destroys the only evidence that could fix the score. A Save on a low-Match company is a labelled disagreement between the user and the model (§8). Gate at the score level and that population never reaches a user, so the system can only ever confirm itself.
    3. It saves nothing. The Apollo credit is spent before the gate runs, and QUEUE_TARGET pages until the queue is full — so discarding results makes the loop fetch more.

    The two jobs separate cleanly: Eligibility admits, Match ranks. A weak match should cost the user a scroll, not a company.

  5. E · Which scorer should become canonical?

    The client's, calculateICPScore — with the caveat that the choice is already made and the alternative is dead.

    calculateFitScore is unreachable and has been for some time. Making it canonical means reviving code that awards full revenue points for having wrong revenue data, ranks a confirmed industry miss above an industry match, weights industry at 30 against location-plus-size at 50, and returns 0 — dropping every company — for a user with no ICP configured. None of that is worth resurrecting.

    calculateICPScore is the better formula on the merits, not merely by default: it normalises over configured dimensions, distinguishes exact from partial matches, treats unconfigured as inactive rather than as failure, and weights industry at 50 where an ICP's meaning actually lives. Its defects — the 'Unknown' string scored as a miss, and coverage being invisible — are fixable inside the function. The server's are structural.

    "Neither-as-written" is the honest label if the question is whether either is ready to be the contract's ScoreICPFitSkill. Neither is, because both score a document that lacks half its inputs. But the consolidation target is unambiguous: one scorer, the client's, moved server-side when the Skill is built, and computed once at a defined trigger rather than recomputed differently by four surfaces.

  6. F · What is the authoritative source of ICP intelligence?

    There isn't one, and that is the decision to make rather than a fact to discover.

    Four stores hold overlapping ICP intelligence (§7). The one Apollo actually searches from — companyProfile/current — is described in code as a cache but is written directly by three surfaces that never touch icpProfiles. The mechanism built to detect the resulting divergence cannot run, because icpSnapshotAtLastReconSave has no writer.

    My recommendation: users/{uid}/icpProfiles/{icpId} is authoritative. It is the only store with a schema, the only one supporting multiple profiles, the only one carrying scoringWeights, and the one icpId on every company document already points at. companyProfile/current becomes a genuinely derived cache with exactly one writer. RECON §3 becomes elicitation that writes through, not a fourth store.

    This is a decision that needs a person, not an investigation. I am recommending, not concluding.

  7. G · What role should RECON play in Scout today?

    Two roles, both of which it can fill with data that exists — and neither of which is influencing Match.

    1. Elicitation. RECON §3 is a well-designed interview for helping a user articulate an ICP. Its output should write through to icpProfiles in the ICP's vocabulary rather than sitting in a parallel store in an incompatible one. That is the whole of §3's legitimate Scout role.
    2. Volume, which it already does. QUEUE_TARGET = min(50 + floor(reconConfidence × 0.5), 100) is the one place RECON changes Scout's behaviour today: a more complete RECON fetches a deeper queue. That is defensible as written — completeness earning volume, not ranking — and it needs no change.

    RECON §4 should not touch Scout at all. Psychographics are buyer-persona intelligence for messaging and tone, they are correctly routed there by RECON_SECTION_MAP, and they have no firmographic content to contribute to Match. This is the cleanest "no" in the report.

    And the six unconsumed §3 fields are a product decision, not an engineering one: either they should feed something (avoidIndustries → Eligibility is the obvious one) or they should stop being asked. Six required questions whose answers nothing reads is a cost the user is paying for nothing.

  8. H · What should we build first?

    Stop fabricating the industry.

    One expression, in saveCompaniesToFirestore (search-companies.js:960):

    - const industry = company.industry || company.primary_industry
-                  || companyProfile.industries?.[0] || 'Unknown';
+ const industry = company.industry || company.primary_industry || null;

    Why this one:

    • It fixes a real user problem. Today a company Apollo could not classify is stamped with the user's own first ICP industry, scores a confirmed match on the heaviest dimension, and is explained to the user with the sentence "Matches your target industry: Financial Services." That is a false statement presented as a finding, and it is the only defect in this report where IDYNIFY actively misleads rather than merely under-informs.
    • It creates no architecture debt, because it is a deletion. No schema change, no new field, no new write path, no decision about Confidence, no dependency on the authority question in F. It removes an inference the system was never entitled to make.
    • It fixes the 'Unknown' defect for free. Writing null instead of the literal string makes resolveIndustry return null, which evalIndustry already handles correctly as UNKNOWN = 50. The 25-point swing in §4.3 disappears without touching the scorer.
    • It makes every later step measurable. Coverage, disagreement detection, and any consolidation all assume the inputs mean what they say. None of them can be evaluated while a dimension is sometimes echoing the user's own input back at them.

    What it costs, stated honestly

    • Companies previously stamped with a fabricated industry keep it. A fix forward does not clean history, and a backfill cannot recover what Apollo never returned — those documents can only be marked, not corrected. That is a separate decision.
    • Surfaces rendering company.industry will receive null. This is the same situation the structural rendering guard pattern already handles in three places in this codebase, and it should be handled the same way rather than by reintroducing a placeholder string.
    • Scores will move for affected companies — from 75 down to 50 in the §4 fixture. That is the score becoming honest, not regressing, but it is user-visible and should be expected.

    Second and third, not now

    Second: return coverage from scoreCompany as a derived value — no schema change, no storage — so consumers can distinguish "we know it fits" from "we know almost nothing." Displaying it needs copy authorisation, which this phase does not carry.

    Third: resolve F. Every consolidation, every Skill, and every drift detector is blocked behind designating an authoritative ICP store, and that is a decision rather than an implementation.

    Not proposed, deliberately: reviving or deleting the dead server scoring block, persisting fit_score at discovery, wiring avoidIndustries, and recording displayed-Match with each swipe. All are worth doing. None is the smallest thing that fixes a real user problem, and each carries a decision this phase has not made.
