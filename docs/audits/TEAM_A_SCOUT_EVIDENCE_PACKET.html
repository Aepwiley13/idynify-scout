§0

Two corrections to the Phase 8 report

Tracing every path end to end for this packet turned up two claims in the Phase 8 report that are wrong. Both are on the accepted-findings list, so they need correcting before Team B tests v0.3 against them.

Correction 1 — the Mission Control finding named the wrong surface.

Phase 8 reported that Mission Control gates on ICP_SCORE_THRESHOLD = 70 against a persisted fit_score discovery never writes, and called it a live user-visible bug. src/pages/Scout/MissionControl.jsx is imported by nothing. It is not routed in App.jsx and no component references it. The threshold, and every read in that file, is dead code.

The routed surface is MissionControlDashboardV2, and it recomputes Match in memory (:775) exactly the way Daily Discoveries does. Those two agree.

The divergence is real but lives elsewhere. SavedCompanies sorts on the persisted fit_score (:145) and CompanyDetail displays it (:965), neither rescoring. For any company discovered since the user last saved their ICP, that value is absent — so a company shown as a strong match in Daily Discoveries sorts as zero in Saved Companies, and its detail page hides the fit line entirely (the fitScore > 0 guard at :988). The accepted finding "Mission Control currently consumes persisted Match state differently from Daily Discoveries" should read "Saved Companies and Company Detail consume persisted Match state; Daily Discoveries and Mission Control V2 recompute it."

Correction 2 — swipe feedback is not unconsumed, and it reveals what icp_score actually is.

Phase 8 said skips feed nothing and that barryRejectionFeedback is read by no code. Both are wrong. barryMissionChat.js:183–206 reads both fields, building an ICP-feedback block for Barry's chat context: the mean of barryFeedback.score, companies rated ≥ 8 with their reasons, companies rated ≤ 4, and free-text notes from both saves and skips.

The correct statement is narrower: a swipe's direction and status drive nothing durable; a swipe carrying structured feedback reaches Barry's chat context and nothing else.

This also resolves the icp_score scale contradiction better than Phase 8 did. barryFeedback has the shape { score: 1–10, reasons: [], note: string } and is supplied by the user, not computed. Document 2's icp_score: 1-10 (from barryFeedback.score) therefore describes a user rating. Document 4's ScoreICPFitOutput.icp_score: 0-100 describes a computed fit. These are two different quantities the contract has collapsed into one field name — not a units disagreement to be settled by picking a scale. v0.3 needs two fields, or one field with an explicit source discriminator.

Everything else on the accepted-findings list held up under end-to-end tracing.

§1

Classification standard

Every row is traced as Producer → Store or derived object → Consumer → Decision and classified by where the chain breaks. The five statuses are disjoint and the distinction between the last three is the one that matters:

StatusMeaningWhere the chain breaks
REACHABLEProducer writes, consumer reads, a decision changes in the running application.Nowhere.
PARTIALThe chain runs, but only some of the intelligence arrives, or it arrives only under some conditions.Mid-chain, conditionally.
DORMANTConsumer code is live and would run, but a required input is never produced, so its branch never fires.At the producer — the code is fine, the data never comes.
DEADThe code cannot execute. No caller, no route, no import.Before the chain starts.
UNREACHABLEData is produced and durably stored, and no consumer exists.After the store — the write succeeds and nothing ever reads it.

Five rows in the tables below fall outside this vocabulary because there is no chain to classify: the evidence is not produced at all (field-level provenance, employee count, location), the concept does not exist (mission-scoped targeting), or the row records a direct contradiction rather than a path. They are labelled as such rather than forced into a status.

DORMANT and UNREACHABLE are opposite failures and are worth keeping apart in v0.3: a dormant consumer is a contract already written that nothing satisfies; an unreachable store is a user answering a question nothing asked.

1 · What currently gives an ICP its identity?

The Firestore document key of users/{uid}/icpProfiles/{icpId}, and nothing else. A user-created profile stores no id field; only the bootstrap-created default does. Identity is therefore a property of where the data is, not of what the data is — so any copy of an ICP body loses its identity by construction. That single fact explains almost every row above.

2 · Where is identity preserved?

  • ICP creation and switching — the key is assigned and used consistently.
  • Company tagging — every discovered company carries an icpId.
  • Queue filtering — both live surfaces filter on it.
  • In-memory Match — computed against the same profile the queue was filtered to.
  • Swipes — swipedForICPId is written when known and omitted when not, which is the correct pattern and the only place in the codebase that uses it.

3 · Where is it lost or defaulted?

  1. The bridge document — the primary loss. One document, one ICP's criteria, no marker.
  2. Five of seven search callers (four after PR #570) — no icpId in the request, and none inferable from the body.
  3. Server default — icpId || DEFAULT_ICP_ID converts "unknown" into a valid-looking assignment.
  4. getActiveIcpId's catch block — an error returns 'default' rather than failing.
  5. recalculateAllScores — writes one ICP's Match onto every company regardless of origin.
  6. Adaptive signals — no scope concept exists at all.

4 · Can two ICPs coexist without contaminating each other?

No. Four distinct contamination paths, in severity order:

PathMechanismEffect
Persisted MatchrecalculateAllScores ignores icpIdSaving ICP B rewrites ICP A's companies with B's scores and B's reasons. The Saved list and every detail page then show A's companies judged by B.
Search resultsFour callers omit icpIdCompanies discovered while ICP B is active are tagged 'default' and become visible only under the default ICP — invisible to B, and mixed into the default's queue.
Discovery targetingBridge-only writers (CompanyQuestionnaire, BarryOnboarding, BarryICPPanel)Editing targeting through those surfaces changes what Apollo searches for on behalf of every ICP, while each profile document is unchanged.
Adaptive signalsNo scope conceptIndustries learned from ICP B's saves steer a search whose results land under 'default'.

Mission Control state and the in-memory queue are not contaminated: both filter and rescore per ICP correctly. The contamination is entirely in what is written, not in what is displayed from memory.

5 · What implicitly assumes one ICP?

  • users/{uid}/companyProfile/current — singular by name, path, and cardinality. The strongest single-ICP assumption in the codebase, and the one every other surface inherits.
  • companies.fit_score / fit_reasons / fit_reason — one value per company for a quantity defined per (company, ICP).
  • recalculateAllScores — iterates the whole collection.
  • The four search callers that pass no icpId — each written as though there were only one thing to search for.
  • DEFAULT_ICP_ID as a fallback rather than an error — encodes "there is always one ICP, and if we don't know which, it's that one."
  • calculateReconConfidence and RECON §3 — workspace-scoped, feeding a per-ICP surface.
  • ICP_LEVEL_SECTIONS = [9] — declares §1–8 workspace-level, which makes RECON §3's firmographic targeting structurally unable to describe more than one ICP.

6 · What must be true for "one authoritative representation per ICP" to hold?

Stated as testable conditions, not as an implementation plan:

  1. Identity travels with the data. An ICP body must carry its own icpId, so that no copy — bridge, request payload, or cache — can exist without it.
  2. Every write that targets discovery names an ICP. No caller may search without one, and the server must reject or quarantine an untagged search rather than default it.
  3. Absent identity is an error, not a value. DEFAULT_ICP_ID must mean "the ICP whose key is default" and never "we don't know."
  4. Match is keyed by the pair. A single-valued fit_score per company cannot represent Match under a multi-ICP invariant. Either Match is never persisted, or it is stored per (company, ICP).
  5. Signals declare their scope. Every derived signal must state whether it is workspace-global (RECON confidence), ICP-scoped (saved industries), or entity-scoped. The repository currently makes no such distinction anywhere.
  6. Legacy untagged records have a defined status. The !c.icpId leak is a deliberate migration accommodation; under the invariant it needs an explicit rule rather than an implicit one.
  7. RECON's scope declaration must match its content. §9 is already per-ICP while §3 is workspace-level. If §3 is to inform per-ICP targeting, that declaration is the thing that has to change first.
Single most consequential finding

ICP identity is a location, not an attribute. Every loss in the chain above is a consequence of copying an ICP body out of its keyed document. A contract that requires one authoritative representation per ICP cannot be satisfied while identity lives only in the path.

The two categories worth Team B's attention are the extremes. The four unreachable rows cover eight distinct pieces of stored intelligence the product asks for and never uses: avoidIndustries, companyType, growthStage, budgetRange, decisionSpeed and marketSize — five of them marked required: true — plus the duplicate section3Answers document. avoidIndustries is the sharpest of these: exclusion intelligence with no enforcement mechanism anywhere in the system. The four dormant consumers are contracts already written in code that nothing satisfies: the ICP drift detector, the Alignment Brief branches keyed to fields Section 3 never writes, and the Learned Intelligence store.

Together they describe a system whose semantic ambition is already encoded and whose producers have not caught up. That gap is the material v0.3 has to resolve.
