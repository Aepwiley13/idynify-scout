Scout Intelligence Architecture · #561–563 · Investigation only

Two Scores, One Name

Before RECON can be connected to Scout, there is a prior problem: IDYNIFY already computes two different fit scores with two different formulas. One decides what enters the queue. The other is what the user sees. They do not agree.

A

Current Match Score

The finding that reframes #561

There is no single Match Score. There are two, computed by different code, with different weights, different arithmetic, and different treatment of missing data.

The server score gates the queue. The client score is what the user reads. A company can be admitted at 62 and displayed at 44.

A scoring defect inside the server formula. Revenue awards its 20 points for having revenue data at all, not for matching the user's range:

if (company.revenue_range) { score += 20; }  — :1333

And when the user skips revenue, the code adds 20 to both numerator and denominator (:1336–1339), which is arithmetically the same as omitting the dimension but reads as a free pass. A company in the wrong revenue band scores identically to one in the right band.

What the number means today: pure ICP fit against four firmographic dimensions — industry, location, employee size, revenue. It is not conversion likelihood, not priority, not relationship strength, and not confidence. Nothing in either formula reads a signal, a behaviour, an interaction, or anything from RECON.

The person-level twin: icp_score exists on the contact schema (peopleSchema.js:230, documented as "0-100 ICP match score") and is used only to sort AllLeads.jsx:1690. No code writes it. It is a declared field with no producer.

B

RECON dimensions, classified

The constraint that decides most of this: a discovered company record holds firmographics and nothing else — industry, employee_count, revenue_range, headquarters_location, founded_year, domain, linkedin_url, phone (search-companies.js:1115–1132). No tech stack, no news, no hiring data, no engagement history. Most RECON dimensions describe people and behaviour, and there is nothing on the company record to compare them against.

The asymmetry worth sitting with. Seven RECON dimensions, ten sections, roughly ninety fields — and one dimension is comparable to what Scout stores. That is not a wiring gap. It is a data gap: RECON collects rich qualitative context about buyers, and Scout holds a firmographic row from Apollo. Connecting them meaningfully requires new data, not new arithmetic.

C

Five concepts, kept separate

They should be distinct. Each answers a different question, changes on a different clock, and fails in a different way. Collapsing them produces a number nobody can act on.

ConceptAnswersChanges whenExists today?
MatchDoes this fit what I said I want? The user edits their ICP Twice, inconsistently — §A
PriorityWhy this one, now? Something happens in the world or in the relationship No — requires an event source IDYNIFY lacks
ConfidenceHow much do we actually know? Data is enriched or goes stale No — and this is the most damaging absence
Relationship intelligenceWhat do we know that explains why this matters? Conversations and activity accumulate Partly — barryContextStack, timeline, brigades
Next actionWhat do I do? The relationship state changes Partly — recommendationEngine, brigade contracts
Confidence is the missing piece that makes everything else honest

The client formula already scores an unknown dimension 50 — the same value as a genuine half-match. A company with no revenue data and a company whose revenue is a partial match are indistinguishable on the card. The server formula is worse: unknown scores 0, so missing data looks exactly like a bad fit, and the <50 filter silently discards companies for being under-enriched rather than for being wrong.

Separating Match ("72% fit on the three dimensions we could check") from Confidence ("we could only check three of four") costs one extra field and immediately makes the score explainable. This is the smallest change with the largest honesty gain, and it needs no RECON integration at all.

Against a blended score. The frozen promise is know who matters, why they matter, and what to do next. A single number answers "who" and destroys "why". If Match, Priority and Confidence are folded together, a 78 cannot be explained — the user cannot tell whether the company fits well, is showing urgency, or is simply well-enriched. Every one of those implies a different next action.

What each issue actually is

IssueAs writtenEvidenceWhat it actually is

A caution about the removed claims. These issues exist because copy was removed for promising unbuilt behaviour. That is not evidence the behaviour should be built. #562 and #563 both require a data source IDYNIFY does not have and has no plan to acquire in the codebase — building either means committing to signal ingestion, not to a scoring change.

Each layer is independently explainable. A user can be told: "Eligible. 72% match on industry, location and size — we could not check revenue. No timing signal. You have no relationship here yet. Suggested next step: intro email." Five sentences, five layers, no opaque number.

Risks

RiskDetail
Reconciling the two formulas changes the queueAdopting the client formula server-side alters which companies clear the <50 gate. Some currently-admitted companies would be excluded and vice versa. Needs a dry run against real data before switching.
Stored scores become stalefit_score is written once at discovery but the client recomputes on every load. Any consumer trusting the stored value — CRM export, admin metrics, engagementSchema — is reading a number the UI disagrees with.
Confidence can look like a downgradeSurfacing "3 of 4 checked" on companies that previously showed a confident 75 may read as the product getting worse. It is getting more honest; the framing matters.
RECON §3 vs ICP profile divergenceTwo stores hold target industries and size today. Users can set them differently and there is no reconciliation. This already produces the "ICP conflict" state RECON warns about.
#562 scope creepSignal detection sounds like scoring work. It is data acquisition — a vendor, a budget and a refresh cadence.

Migration implications

Nothing proposed here requires a schema migration. fit_score keeps its name and range. A confidence value is additive and absent-tolerant. icp_score on contacts is currently unwritten, so giving it a producer breaks nothing. The one genuinely breaking change would be consolidating RECON §3 with icpProfiles, which is the largest item and the one I would not start with.

F

Smallest valuable implementation

Ordered by value per unit of risk. None of it is #561 as written.

  1. STEP 1

    One formula, one place

    Import icpScoring.js into search-companies and delete calculateFitScore. Fixes the revenue defect, ends the admitted-at-62 / displayed-at-44 divergence, and makes the <50 gate mean what the card means. Pure consolidation — no new concept.

    Highest value · needs a dry run on real data first · no RECON involvement
  2. STEP 2

    Separate Confidence from Match

    Return { score, confidence, checked, total } from the scorer. Stop scoring unknown dimensions as 50 inside the match number; report them as unchecked instead. Display "72% · 3 of 4 checked".

    Additive · makes the existing score explainable · unblocks the "why" half of the promise
  3. STEP 3

    Make eligibility explicit and visible

    Move avoidIndustries and the founding-age filter out of the score and into a named eligibility pass that records why a company was excluded. Today a company can be silently dropped and the user cannot find out why.

    Small · directly serves explainability · currently invisible to users
  4. STEP 4

    Decide the ICP store question — #561, reframed

    RECON §3–4 and icpProfiles hold the same firmographic targeting twice. Consolidate, or declare one authoritative and make the other read-only. This is the real #561 and it is a product decision, not an integration.

    Largest · breaking · do not start here
  5. HOLD

    #562 and #563 stay closed until there is a data source

    Both need per-company signal or vendor data that no current integration returns. Reopen them as data-acquisition decisions, not scoring work.

    Blocked on data, not on design
