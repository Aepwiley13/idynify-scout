1. Executive Summary

The current onboarding flow collects intelligence from new users, then silently loses most of it. Barry emerges from onboarding with near-total amnesia — unable to reference what the user told him, unable to find companies for them, and unable to provide a guided first experience.

What onboarding actually does today

A new user signs up (email + password), pays via Stripe, and is routed to one of two onboarding paths. CheckoutSuccessPage.jsx:13 navigates to /onboarding/barry (legacy BarryOnboarding), while SmartRedirect in App.jsx:321 routes to /onboarding (live OnboardingFlow). Both paths exist and are reachable. The live OnboardingFlow collects a website URL, runs AI analysis, asks 4 ICP questions, offers Gmail connect, then attempts to show matched companies. It finds zero for every new user because it never triggers company discovery. The legacy BarryOnboarding runs a conversational ICP interview, triggers search-companies, and sets the state fields Mission Control needs.

Top 10 Findings

F1 — CRITICAL

OnboardingFlow writes ICP answers to dashboards/{uid} via updateDoc, but this document is never created. .catch(() => {}) silently discards the Firestore error. Every user's Step 3 answers are lost.

F2 — CRITICAL

OnboardingFlow never triggers company discovery. Step 5 reads users/{uid}/companies which is empty for new users. The promise of "ten matched companies" is undelivered.

F3 — CRITICAL

FirstRunView gate requires onboardingSource === 'barry_onboarding' which only the legacy flow sets. New users from OnboardingFlow skip the welcome experience and land on an empty dashboard.

F4 — CRITICAL

Barry has two incompatible context systems. Client-side barryContextStack.js provides business/RECON breadth. Server-side barryContextAssembler.js provides per-contact memory depth. No surface receives both. Mission Control Barry knows the business but not relationships; Hunter Barry knows relationships but not the business.

F5 — HIGH

CheckoutSuccessPage.jsx:13 routes paying users to /onboarding/barry (legacy), not /onboarding (live). The two flows write different state, store data differently, and set different completion flags.

F6 — HIGH

RECON Section 3 (Target Market, weight 15, the most critical section for company discovery) is excluded from the client-side context pipeline. It only reaches Barry through a shared 2000-char server budget where it competes with 9 other sections.

F7 — HIGH

track-outcome.js — the most common outcome recording path — never calls barryOutcomeAttribution. Outcomes recorded through Hunter bypass the entire learning loop. The attribution engine only fires through Barry's own engage sessions.

F8 — HIGH

RECON is a static questionnaire, not a living intelligence model. No system event, user behavior, engagement outcome, or external data source ever updates RECON answers. 105 questions across 10 sections, stored with no provenance, no confidence, no timestamps, no staleness repair.

F9 — MEDIUM

Three overlapping intelligence collection surfaces (RECON, CompanyQuestionnaire, ImprovedScoutQuestionnaire) save to different Firestore paths with no cross-referencing. Three overlapping contact state fields (contact_status, hunter_status, relationship_state) with no reconciliation.

F10 — MEDIUM

No formal intelligence lifecycle. No staleness detection (inferred values never expire), no versioning (overwritten without history), no confidence scores, and contradiction resolution exists only for relationship warmth. All other fields silently win based on write order.

3. Current Intelligence: World / People / Intent / Rules

A. Business / World Intelligence

Barry receives RECON data through two pipelines:

  • Client pipeline (barryContextStack.js): Loads RECON sections 1, 2, 4, 5, 9 from dashboards/{uid}, trimmed to 300 chars each. Provides ICP profile from icpProfiles or companyProfile/current fallback. Used by Mission Control chat.
  • Server pipeline (reconCompiler.js referenced in Netlify functions): Compiles all 10 sections into a 2000-char budget. Used by message generation functions. Note: reconCompiler.js in src/utils/ appears to have no importers — the server-side functions may use inline compilation.
Gap
Section 3 (Target Market Firmographics, weight 15) is excluded from the client pipeline — RECON_SECTION_MAP maps sections 1, 2, 4, 5, 9 only. The most important section for company discovery never reaches Mission Control Barry. Website URL and LinkedIn URL are collected by the Scout questionnaire but never passed to Barry.

B. Relationship / People Intelligence

Per-contact context is assembled by barryContextAssembler.js (server-side) and barryMemoryService.js (client-side). Barry receives:

  • Identity: name, title, company, email
  • Relationship classification: relationship_state, warmth_level, known_contact
  • Memory: barry_memory on contact doc (what worked, what didn't, channel history, preferences, new facts)
  • Engagement stats: sessions count, last outcome, channels tried
  • Engage state: current status, brigade assignment
Stored but not available to Barry
Gmail message content, Apollo enrichment data, referral graph relationships, engagement_timeline subcollection events, brigade_history transitions, enrichment_provenance per-field source tracking. All stored in Firestore; none assembled into any Barry prompt.

C. Intent / Objective Intelligence

No single canonical "user objective" exists. Intent is distributed across:

  • Missions (users/{uid}/missions): Have outcome_goal field, but missions are per-contact engagement plans, not user-level objectives
  • Session modes: Runtime classification of 13 intent types by Claude (inquiry, follow_up, objection, etc.) — ephemeral, not persisted
  • Brigade contracts: Define behavior cadence per contact tier, not user goals
  • Engagement intent: Selected per-contact in Hunter (e.g., "Schedule meeting", "Get referral") — contact-scoped, not user-scoped

There is no persistent cross-module representation of "what the user is trying to accomplish right now."

D. Permission / Action Intelligence

No formal permission model. Barry's action surface is defined entirely by the JSON output schema in each system prompt. All actions requiring state changes go through client-side confirmation (user clicks "Send", "Approve", etc.). There is no stored user preference for what Barry may autonomously research, recommend, draft, send, modify, or automate.

Scope confusion
No business or workspace entity exists. All business intelligence (ICP, RECON, value proposition, competitors, market) is stored under user-scoped paths. Temporal Scope Findings

The platform makes no distinction between permanent truth and temporary context. Examples of intelligence treated identically:

6. Barry Context Assembly Map

This is the most architecturally significant finding. Barry's intelligence is split across two incompatible context assembly systems that never merge.

System A: Client-Side (barryContextStack.js)

Used by: Mission Control BarryChatPanel (the primary user chat surface)

Provides:

  • All contacts (up to 500): name, title, company, relationship_state, status, stage
  • Active missions: status, steps, last outcome
  • RECON sections 1, 2, 4, 5, 9 (300 chars each)
  • RECON confidence score
  • Active ICP profile messaging fields

Does NOT provide: Per-contact barry_memory, strategy stats, session history, engagement history, what worked/didn't work

System B: Server-Side (barryContextAssembler.js)

Used by: generate-engagement-message, barryHunterGenerateStep, barryHunterProcessEngage

Provides:

  • Per-contact barry_memory: what worked, what didn't, channels tried, preferences, new facts
  • Per-user barry_memory: strategy_stats, aggregate outcomes
  • Recent barry_sessions (last 5)
  • Prompt-ready context string (1200 char / ~300 token budget)

Does NOT provide: RECON data, ICP profile, business positioning, value proposition, competitors, target market, other contacts, missions

Split-brain architecture

Mission Control Barry (where users chat) knows the business but not the relationships. It sees 500 contact summaries but has zero memory of past conversations with any of them. It cannot say "Last time we tried a direct approach with Sarah and it didn't work."

Hunter Barry (where messages are generated) knows the relationships but not the business. It has deep per-contact memory but zero RECON/ICP context. It cannot reference the user's value proposition, competitive differentiators, or target market when drafting outreach.

No surface receives both.

Storage

Answers are stored in dashboards/{uid} as flat fields grouped by section key. Questions are defined inline in individual React component files (Section1Foundation.jsx through Section10BehavioralSignals.jsx) with no shared schema or question registry.

Key Findings

  • Triple-write storage: Raw answers in section fields, AI-generated output in sectionOutput fields, dashboard-level aggregates in onboarding fields. No reconciliation between the three.
  • No provenance: No field-level timestamps, authorship tracking, confidence scores, or edit history. Cannot distinguish user-typed from AI-populated from analyze-website-populated.
  • No progressive learning: No system event, user behavior, engagement outcome, or external data source ever updates RECON data. The reconHealth.js staleness system detects decay (calculates completion %) but cannot repair it.
  • Three overlapping questionnaires: RECON (src/components/recon/), CompanyQuestionnaire (src/components/scout/CompanyQuestionnaire.jsx), and ImprovedScoutQuestionnaire (src/components/ImprovedScoutQuestionnaire.jsx) all collect business intelligence and save to different Firestore paths.
  • RECON is a questionnaire, not an intelligence model. It collects and stores answers but has no concept of confidence, freshness, source priority, or automated update.

Critical Learning Gaps (ranked by impact)

  1. track-outcome.js bypasses attribution. The most common outcome recording path (Hunter tracker) never calls barryOutcomeAttribution. The learning loop only fires through Barry's own engage sessions. Evidence: track-outcome.js writes to learnings collection but does not import or call any function from barryOutcomeAttribution.js.
  2. Auto-detected Gmail replies don't trigger attribution. gmail-poll-replies.js detects replies and updates contact_status to "In Conversation" but never connects the reply to the Barry session that generated the message. The reply-to-strategy correlation is lost.
  3. Scout swipes are not learned from. Every accept/reject is recorded with full ICP context (swipedForICPId, barryFeedback) but no service analyzes patterns to refine company discovery.
  4. Message editing is invisible. User edits to Barry's generated messages are never compared to the original. If a user consistently removes humor or shortens messages, Barry cannot learn that preference.
  5. Inbox analysis is ephemeral. Claude's analysis of inbound emails (intent, sentiment, commitments, urgency) influences only the current session. Results are not persisted to contact intelligence.

10. Duplication / Fragmentation / Contradiction

Duplicate Truths

  • ICP / business positioning: dashboards/{uid} (RECON), icpProfiles/{id}, companyProfile/current — three sources, no sync
  • Onboarding completion: onboarding.completed (nested) vs onboardingComplete (top-level) — different flows write different fields
  • Contact status: contact_status, hunter_status, relationship_state — three overlapping state machines on the same contact document
  • Messaging/voice: RECON Section 9 vs ICP profile messaging fields vs companyProfile/current messaging — three potential sources of messaging guidance

Fragmented Intelligence

  • Business intelligence collection: RECON, CompanyQuestionnaire, ImprovedScoutQuestionnaire — three surfaces saving to different paths
  • Context assembly: Client-side stack and server-side assembler — two systems with zero overlap
  • Onboarding paths: OnboardingFlow and BarryOnboarding — two active paths writing different data

Contradiction Resolution

One pattern exists: inferRelationshipWarmth.js checks relationship_state_source. If "user_set", Barry creates a barry_warmth_suggestion instead of overwriting — the system defers to the user while surfacing the disagreement.

Everywhere else: First-write wins. CANONICAL_FIELDS protection in contactIdentityService.js prevents enrichment from overwriting user edits, but disagreements are never surfaced. If Apollo says "VP of Sales" and the user typed "Director of Sales", the user's value is protected but no notification says "Apollo disagrees."

11. P0 Break Verification

B1 — Dashboard Initialization VERIFIED

  • File: src/pages/Onboarding/OnboardingFlow.jsx, handleFinishQuestions, line 426
  • Current behavior: updateDoc(doc(db, 'dashboards', userId), reconFields) is called but dashboards/{userId} does not exist for new users. initializeDashboard() is never called in the OnboardingFlow path. Firestore's updateDoc throws on a missing document.
  • Error handling: .catch(() => {}) silently swallows the error. The outer try/catch block has /* best effort */.
  • Root cause: OnboardingFlow was built without calling initializeDashboard first. The dashboard document is created elsewhere (RECON page, or legacy flows) but never during this onboarding path.
  • Blast radius: Every new user's Step 3 answers (idealCustomerTypes, excludedIndustries, valueProposition, perfectCustomer) are silently lost. These are the only user-provided ICP signals in OnboardingFlow.
  • Proposed minimal fix: Call initializeDashboard(userId) before the updateDoc, or switch to setDoc(..., { merge: true }).

B2 — Step 5 Discovery VERIFIED

  • File: src/pages/Onboarding/OnboardingFlow.jsx, loadCompanies useEffect, lines 444-513
  • Current behavior: Step 5 only reads users/{userId}/companies with getDocs(companiesRef) (line 462). No where() clause, no status filter. For new users, this collection is empty.
  • Root cause: OnboardingFlow never calls search-companies or any discovery function. The legacy BarryOnboarding.jsx (line 370) correctly triggers fetch('/.netlify/functions/search-companies', ...) but the new flow does not replicate this.
  • Blast radius: Every new user through OnboardingFlow sees "I found 0 companies" at Step 5, then an empty list at Step 6 with the message "No companies matched yet."
  • Proposed minimal fix: Trigger search-companies after Step 3 (when ICP data is available), before showing Step 5 results. Or mirror BarryOnboarding's pattern of setting barryState: 'SEARCHING' and delegating to Mission Control.

B3 — Mission Control First-Run VERIFIED

  • File: src/pages/Scout/MissionControlDashboardV2.jsx, lines 874-877
  • Gate condition:
const isFirstRun = obComplete === true && onboardingSource === 'barry_onboarding' && hasSeenMCWelcome === false;
  • Current behavior: OnboardingFlow never writes onboardingComplete (top-level), onboardingSource, hasSeenMCWelcome, or barryState. It only writes onboarding.completed (nested), which is a different field. The gate evaluates to false for every OnboardingFlow user.
  • Root cause: The FirstRunView gate was designed for BarryOnboarding's completion signature. OnboardingFlow uses a different field structure (onboarding.completed vs onboardingComplete).
  • Blast radius: Every new user from OnboardingFlow bypasses FirstRunView and lands on the regular (empty) Mission Control dashboard. No welcome guidance, no search-in-progress indicator, no "Barry is finding companies" state.
  • Proposed minimal fix: When OnboardingFlow marks completion, also write the four fields Mission Control expects: onboardingComplete: true, onboardingSource: 'onboarding_flow', hasSeenMCWelcome: false, barryState. Update the FirstRunView gate to accept the new source value.
Chain-linked breaks
The three P0 breaks are not independent. B1 loses the ICP answers that should drive company discovery. B2 means no companies are found even if the answers survived. B3 means the welcome experience that should show "Barry is finding companies" never triggers. A new user completing OnboardingFlow arrives at an empty dashboard with lost data, zero companies, and no guidance.

14. Minimum Viable Understanding

Technically Required Today

What Barry must know to function at all in the current codebase:

  • User authentication (email, uid) — required for Firestore access
  • Subscription tier — gates credit usage and feature access
  • At least one contact — required for any engagement flow
  • Contact identity (name, email) — required for message generation

Product Assumptions Treated as Required

What the current flow treats as required but may not be:

  • Website URL — used for analyze-website but not stored. Not technically needed if business intelligence comes from other sources.
  • 4 ICP questions — collected but silently lost (B1). Even when stored, only reachable via RECON path, not via ICP scoring or company discovery directly.
  • Gmail connection — offered at Step 4 but skippable. Not used for anything during onboarding itself.
  • Complete RECON — 105 questions weighted as if all are needed before value delivery. But Barry's engagement attribution, warmth inference, NBS, and strategy recommendations all work with zero RECON data.

Discoverable / Inferable Today

What Barry could already know without asking the user:

  • Company name, industry, size, location — analyze-website already extracts these from the website. Currently stored in RECON but could populate ICP directly.
  • Product/service description — extracted by analyze-website AI analysis
  • Competitors — partially discoverable from website content
  • Value proposition — extractable from website copy
  • Target personas — inferable from website "for whom" sections
  • User's existing relationships — discoverable from Gmail if connected
  • Communication style preference — inferable from message editing patterns (not currently tracked)

15. Open Product Decisions

These cannot be resolved from the codebase alone.

  1. Which onboarding path is canonical? OnboardingFlow and BarryOnboarding both exist and are both reachable. CheckoutSuccessPage sends to one; SmartRedirect sends to the other. They write different data, set different completion flags, and create different post-onboarding states. The platform needs one path.
  2. Is "ten matched companies" the universal first-value moment? The audit reveals multiple partial first-value paths. A user with a strong existing network might get more value from "Barry identified three relationships that can help" than from ten cold companies. Does first value vary by user intent?
  3. Should the business/workspace entity be explicit? All business intelligence is currently stored under user-scoped paths. If IDYNIFY will support teams or multi-user businesses, a workspace entity needs to be created. If single-user only, the current approach works but should be documented as intentional.
  4. What should Barry be allowed to do autonomously? Currently all actions require user confirmation. The eventual vision mentions "what Barry is allowed to research, recommend, draft, change, send, automate, or execute." Where on this spectrum should Barry start for a new user?
  5. How should temporary strategy vs permanent truth be distinguished? "We sell SaaS to mid-market healthcare" and "this quarter we're focused on Utah nonprofits" are stored identically. Should temporary context expire? Should Barry ask "is this still true?" periodically?
  6. What is the minimum information Barry needs before providing value? The current flow collects website + 4 questions + optional Gmail before showing (empty) results. How much of this is truly required vs. delayable? Could Barry provide value with just a website URL?
  7. Should RECON evolve from questionnaire to living model? The 105 RECON questions capture valuable intelligence, but the questionnaire form factor requires manual completion and never updates. Should answers update from engagement results, website changes, and behavioral signals? If yes, what is the provenance/confidence model?
  8. How should the two context assembly systems merge? The split-brain architecture (F4) is the highest-value technical fix. Should the server assembler expand to include RECON/ICP, or should the client stack expand to include per-contact memory? Or should a unified service replace both?
