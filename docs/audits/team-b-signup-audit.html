Error Handling

Firebase error codes are mapped to user-friendly messages:

  • auth/email-already-in-use → "An account with this email already exists." LEAKS INFO
  • auth/invalid-email → "Please enter a valid email address."
  • auth/weak-password → "Password is too weak. Please use at least 6 characters."
  • auth/too-many-requests → "Too many attempts. Please try again later."
  • Default → "Failed to create account. Please try again."

Loading / Success States

  • Loading state: None. No spinner, no button disable. The CTA remains clickable during submission, allowing duplicate submissions.
  • Success state: No success indicator shown. User is navigated to /checkout immediately.
  • Duplicate submission protection: None. Rapid double-clicks will call createUserWithEmailAndPassword twice (Firebase will reject the second, but the first Firestore write may race).

Post-Signup State

  • Email verification: None. sendEmailVerification() is never called.
  • Welcome email: Sent via Resend API (fire-and-forget, no auth required on endpoint).
  • Redirect destination: /checkout?tier={tier}
  • Analytics events: None fired at signup.
  • Stripe/billing: No interaction at signup step. Stripe is only invoked at checkout.
  • Trial or credit allocation: Credits written immediately at signup (before payment). See VULN-4.

Section 6

Gmail Authorization Separation

Are identity auth and Gmail data access separated?

Yes, completely. They are separate systems with no code overlap:

  • Identity auth: Firebase Auth (email/password). No Google scopes requested.
  • Gmail data access: Custom OAuth2 flow via Netlify Functions (netlify/functions/gmail-oauth-init.js). Uses GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET. Tokens stored at users/{uid}/integrations/gmail.

OAuth Scopes

SystemScopes
Firebase Auth (identity)None — email/password uses no OAuth scopes
Gmail integration (data)gmail.readonly, gmail.send, gmail.modify (inspection needed to confirm exact scopes from gmail-oauth-init.js)

Can a user create an account without granting Gmail access?

Yes. Gmail connection is completely optional. It is offered at onboarding Step 4 with a “Skip for now” option. The onboarding flow derives Gmail connection status live from users/{uid}/integrations/gmail (src/hooks/useOnboardingState.js:54-58).

Can Gmail access be granted later?

Yes. The Hunter module offers Gmail connection at any time. The GmailConnectButton component is used in both onboarding and in-product contexts.

Recommendation: When Should Gmail Authorization Occur?

Recommended: During onboarding, with Barry providing context (current approach)

The current architecture already implements Aaron's preliminary direction correctly. Gmail authorization happens at onboarding Step 4, after the user has created their account and begun interacting with Barry. This is the right moment because:

  • Trust is established. The user has already seen Barry analyze their website and ask intelligent questions. They understand what Barry does before they're asked to share Gmail.
  • Context is provided. Barry explains: “I can write personalized outreach and send it from your inbox. To do that, I just need permission.”
  • Skip is frictionless. The user can skip and connect later when they encounter a Gmail-dependent feature.

Do not move Gmail authorization to signup. Asking for Gmail access before the user understands what the product does will damage trust and reduce conversion.

If Google Sign-In is added: Firebase Auth identity (Google sign-in) and Gmail data access must remain completely separate OAuth consent screens. The Google sign-in button requests only email and profile scopes. Gmail read/send scopes are only requested later during onboarding or first use. This is already the case architecturally — the concern is only relevant if someone attempts to combine them.

Section 9

Security & Privacy Audit

VULN-1 Privilege Escalation via Self-Writable Role Field CRITICAL

Files

firestore.rules:6-9, netlify/functions/utils/adminAuth.js:36-44

Problem

Firestore rules grant any authenticated user full write access to their own document: allow write: if request.auth.uid == userId. The checkAdminAccess() function reads users/{userId}.role from Firestore and grants admin access if role === 'admin'. Any user can set role: 'admin' on their own doc from the browser console and gain access to all admin Netlify Functions: user management, impersonation, audit log export, account suspension, password resets.

Impact

Complete admin takeover. Every authenticated user is one Firestore write away from full admin access.

Fix

Move role to a separate admin-only collection, add field-level validation in Firestore rules preventing writes to role, or rely exclusively on the ADMIN_USER_IDS env var and remove the Firestore role check.

VULN-2 Payment Gate Bypass via Self-Writable hasCompletedPayment CRITICAL

Files

firestore.rules:6-9, src/App.jsx (ShellRoute, ProtectedRoute, SmartRedirect)

Problem

The entire payment gate relies on users/{uid}.hasCompletedPayment === true. Since users can write any field to their own doc (same Firestore rules issue), any authenticated user can set this field from the browser console and bypass Stripe entirely. They can also set subscriptionTier: 'pro' and credits: 99999.

Impact

Full product access without paying. Unlimited credits.

Fix

Use Firebase custom claims (server-only, not client-writable), move payment status to a separate collection, or add Firestore rules that prevent client writes to payment-related fields.

VULN-3 Dev Mode Payment Simulation in Client Bundle HIGH

File

src/pages/CheckoutPage.jsx:86-118

Problem

When VITE_STRIPE_ENABLED !== 'true', the checkout page writes hasCompletedPayment: true and full credit allocation directly to Firestore from the client. Even if the var is set correctly in production, the dev-mode code path is visible in the shipped JavaScript bundle, documenting the exact Firestore fields needed to fake a payment.

Fix

Remove dev-mode payment simulation from the client. If needed for testing, implement as a server-side Netlify Function with dev-only env var gating.

VULN-4 Credits Allocated Before Payment HIGH

File

src/pages/Signup.jsx:58-69

Problem

At signup, the user doc is created with credits: 400 (or 1250) and hasCompletedPayment: false. If any code path checks credits without also checking payment status, an unpaid user could consume enrichments. Additionally, the credits data shape changes from integer (signup) to object (post-payment webhook), creating inconsistency.

Fix

Do not write credits at signup. Let the Stripe webhook be the sole authority for credit allocation.

VULN-5 Unauthenticated Welcome Email Endpoint MEDIUM

File

netlify/functions/send-welcome-email.js

Problem

The endpoint accepts any POST with { email, userId } and sends a branded email from Aaron Wiley <aaron@idynify.com>. No authentication, no rate limiting, no verification that the email matches the user. Can be used to send unlimited branded emails to arbitrary addresses.

Fix

Add verifyAuthToken() and validate the email matches the authenticated user's email.

VULN-6 No Email Verification MEDIUM

After createUserWithEmailAndPassword, no email verification is performed. Users can sign up with emails they don't own. Combined with VULN-5, the signup flow can be used to send branded emails to arbitrary addresses.

VULN-7 No Bot Protection on Signup MEDIUM

No CAPTCHA, rate limiting, or bot detection on the signup form. Firebase Auth has its own rate limiting per-IP, but combined with VULN-5, bots can create accounts and trigger mass email sending.

VULN-8 Auth Error Messages Reveal Email Existence MEDIUM

Signup: “An account with this email already exists” confirms the email is registered. Forgot password: “No account found with this email address” confirms the email is NOT registered. Together, these allow email enumeration.

Fix

Use a generic message for both cases: “If an account exists with this email, you'll receive instructions.” Firebase Auth can be configured to prevent email enumeration (Email Enumeration Protection).

VULN-9 Hardcoded Firebase Configuration LOW

Firebase config is hardcoded in src/firebase/config.js with project ID idynify-scout-dev instead of reading from VITE_FIREBASE_* env vars. Firebase client config is inherently public, so the security impact is low, but it prevents environment separation.

VULN-10 No Terms Acceptance Captured LOW

The signup form has no Terms of Service checkbox, no Privacy Policy link, and no record of user consent. No termsAccepted field is written to the user doc. No terms or privacy policy pages exist in the codebase.

[NEEDS AARON] Do terms of service and privacy policy exist? Are they hosted elsewhere? Legal requirement for signup.

Section 12

Signup → Onboarding Handoff

What happens immediately after signup

After signup, the user lands on /checkout. After completing payment, they land on /checkout/success, which redirects to onboarding. There is a split in the onboarding entry point:

PathDestinationFlow TypeWhen
CheckoutSuccessPage auto-redirect /onboarding/barry Legacy conversational ICP builder (BarryOnboarding.jsx) User completes payment and stays on success page
CheckoutSuccessPage manual CTA /onboarding/barry Same legacy flow User clicks “MEET BARRY NOW”
SmartRedirect (App.jsx) /onboarding New 6-step wizard (OnboardingFlow.jsx) User navigates away and returns, or visits / while logged in

The two onboarding flows

  • Legacy (/onboarding/barry): Conversational. Barry asks freeform questions to build ICP. Uses Claude API for natural language processing. Saves ICP data to users/{uid}/companyProfile. Does not use the useOnboardingState hook — manages its own state independently.
  • New (/onboarding): 6-step wizard. Step 1: Meet Barry. Step 2: Website analysis. Step 3: Smart questions. Step 4: Gmail connection. Step 5: Build prospect list. Step 6: First prospects. Uses useOnboardingState hook with Firestore flags at users/{uid}.onboarding.

Information duplicated between signup and onboarding

Significant overlap exists:

  • Feature descriptions (“Define your ICP with AI-powered RECON”) appear on signup and are explained again in onboarding
  • Barry’s identity is introduced on signup (large avatar, “Barry AI” headline) and re-introduced in onboarding Step 1
  • Product capabilities (Scout, RECON) are listed on signup and demonstrated in onboarding

What can be removed from signup

Because the user encounters Barry within 60 seconds of completing signup (via onboarding), the following signup elements are redundant:

  • Barry avatar and “Barry AI” headline — Barry introduces himself in onboarding Step 1
  • Mission Briefing box — product education belongs in onboarding
  • Feature bullets — onboarding demonstrates these capabilities interactively
  • “Data Exploration • Lead Discovery • Mission Ready” — marketing language, not needed for account creation

Current first-value moment

Onboarding Step 6: “Here are your top matches.” Barry shows the user companies ranked by ICP fit score. This is the first moment the user sees the product doing something for them. Total time from CTA press: ~3–7 minutes (happy path with skipping optional steps).

What it should be

The first-value moment is correct. The onboarding flow is well-designed — Barry analyzes the business, asks targeted questions, and delivers prospects. The problem is what comes before onboarding: signup and checkout add ~2 minutes of friction before the user reaches Barry.

Backend processes adding latency

  • Welcome email (await fetch): Adds 0.5–2s to signup despite being non-critical. Should be truly fire-and-forget (remove await).
  • Stripe webhook processing: Runs asynchronously after Stripe redirects. If the webhook hasn't fired before the user reaches the success page, the user doc may not yet have hasCompletedPayment: true. The success page doesn't verify payment status — it trusts the redirect.
  • Website analysis API: Calls /.netlify/functions/analyze-website. This is a Claude API call that can take 5–15 seconds. Good loading UX with stepped progress, but the latency is real.

Three Modernization Options (Backend Perspective)

Option A — Minimum Viable Fix

What changes

  • Remove fake countdown timer and false “Limited Seats” badge
  • Fix password fields: add show/hide toggle, autocomplete attributes, accessible labels
  • Add loading state and duplicate submission protection to signup CTA
  • Remove await on welcome email (true fire-and-forget)
  • Fix starter tier contact claim (“email & phone” → “email only”)
  • Update branding: IDYNIFY leads, Barry/Scout demoted

What stays

  • Email/password auth (no Google, no OTP)
  • Same checkout flow (separate page → Stripe)
  • Same Firestore data model
  • Firestore security rules unchanged (VULN-1 and VULN-2 remain)

Backend risk

HIGH — VULN-1 (admin takeover) and VULN-2 (payment bypass) remain exploitable. These should be fixed regardless of which option is chosen.

Effort

1–2 days frontend changes. Security fixes (Firestore rules) are an additional 1 day and should be mandatory.

Option B — Modernized Signup

What changes

  • Everything in Option A
  • Add “Continue with Google” (Firebase Auth Google provider)
  • Simplify form: IDYNIFY wordmark, one-line value statement, email/password + Google, Terms/Privacy inline
  • Remove product education from signup (Mission Briefing, feature bullets, Barry avatar)
  • Fix Firestore rules: field-level validation preventing client writes to role, hasCompletedPayment, credits, subscriptionTier, subscriptionStatus
  • Don't write credits at signup — let webhook be sole authority
  • Add auth to welcome email endpoint
  • Fix onboarding split: CheckoutSuccessPage redirects to /onboarding (new flow), not /onboarding/barry

What stays

  • Separate checkout page → Stripe Payment Link
  • Password option (alongside Google)
  • Current onboarding 6-step flow

Backend risk

LOW — Security fixes are included. Google Auth is well-supported by Firebase. Main risk is handling the “Google email matches existing email/password account” edge case (Firebase has built-in account linking).

Effort

3–5 days. Firebase rules refactor (1 day), Google Auth (1 day), signup page simplification (1 day), welcome email auth + onboarding redirect fix (1 day).

Option C — Best-in-Class

What changes

  • Everything in Option B
  • Add OTP/magic link option (Firebase email link sign-in) — eliminates password fields entirely for users who prefer it
  • Move payment gate from Firestore field to Firebase custom claims (server-only, not client-writable)
  • Add email verification before proceeding to checkout
  • Add signup funnel analytics events at each stage
  • Remove dev-mode payment simulation from client bundle
  • Add bot protection (Firebase App Check or reCAPTCHA)
  • Fix email enumeration (generic error messages)
  • Add Terms/Privacy acceptance tracking in user doc
  • Eliminate 3-second success page delay — direct to onboarding
  • Handle split-state edge case: if Firestore write fails after auth creation, retry or provide recovery path

Ideal auth + onboarding flow

/signup
  → IDYNIFY wordmark + "Find your next customers"
  → [Continue with Google] or [Email + OTP]
  → Terms/Privacy inline acceptance
  → Email verification (if email/password)
  → /checkout (Stripe)
  → /onboarding (6-step, no legacy split)
     Step 1: Barry introduces himself
     Step 2: Website analysis
     Step 3: Smart questions
     Step 4: Gmail (deferred, with Barry context)
     Step 5: Prospect list generation
     Step 6: First value — "Here are your matches"
  → /mission-control-v2

Backend risk

LOW — All security issues addressed. Firebase custom claims are the industry-standard approach for server-managed authorization. OTP is a proven Firebase capability.

Effort

7–10 days. Includes all security fixes, custom claims migration, OTP implementation, analytics instrumentation, and edge case handling.

Recommendation: Option B

Option B delivers the highest value per unit of effort. It addresses all critical security vulnerabilities, simplifies the signup experience to match the audit brief's target architecture, and adds Google Auth — the single largest conversion improvement available. The onboarding flow (post-signup) is already well-designed; the problem is getting users to it.

Option C's additions (OTP, custom claims, App Check) are individually valuable but can be phased in after the core redesign ships. Option A leaves critical security issues unresolved and should not ship.

Minimum: fix VULN-1 and VULN-2 regardless of which option is chosen. These are exploitable today.
