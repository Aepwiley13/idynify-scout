1. Definition of Barry Intelligence

Barry knows something when all of the following are true:

  1. He has a defined piece of intelligence about a known subject — not a raw data field, but a fact with meaning he can act on.
  2. He understands where it came from and how trustworthy it is — a user assertion, an AI inference, a third-party enrichment, or an observed behavior, each carrying different weight.
  3. He knows how long it should remain valid — a durable business truth, an evolving relationship state, a temporary strategy, or a mission-scoped objective.
  4. He knows what evidence may change it — which observations, outcomes, or user actions should trigger re-evaluation.
  5. He can apply it to a relevant decision or objective — intelligence that cannot reach any surface or influence any action is stored data, not knowledge.

Intelligence that fails any of these conditions is incomplete. It may still be useful — raw data can become intelligence when the missing conditions are added — but Barry should not treat it with the same authority as intelligence that satisfies all five.

The gap today: Most of IDYNIFY's stored data satisfies condition 1 (a defined fact) but fails conditions 2–5. RECON answers have no provenance (2), no temporal scope (3), no update triggers (4), and several sections never reach any Barry surface (5). The Intelligence Contract exists to close these gaps systematically.

2. Governing Rules

Two permanent product principles govern all intelligence operations. These are not guidelines — they are constraints that every future system must satisfy.

Barry's Question Rule

Discover what you can. Infer what you reasonably can. Confirm what matters. Ask only what you cannot know and need now. Learn everything else over time.

This rule establishes a priority order for intelligence acquisition. Barry's first instinct is never to ask the user — it is to discover (from websites, email, public data), then infer (from behavior, patterns, outcomes), then confirm (verify inferences that carry high consequence), and only then ask (when a decision requires information that cannot be discovered, inferred, or deferred). Everything that isn't immediately needed enters the "learn over time" path — Barry accumulates it passively from ongoing interactions.

Why this matters: Every question Barry asks is a withdrawal from the user's patience. The onboarding that asks 105 questions before delivering value violates this rule. The onboarding that analyzes a website, infers the business, confirms one critical assumption, and starts working — that follows it.

Barry's Intelligence Rule

Never collect intelligence without knowing who it belongs to, where it came from, how trustworthy it is, how long it should remain true, and what decisions it should improve.

This rule prevents the accumulation of unstructured data that no system reads. Today, engagement_timeline subcollections are written but never consumed. enrichment_provenance is tracked but never surfaced. Scout swipes are recorded with full context but produce zero learning. Each of these violates the Intelligence Rule: they collect without knowing what decisions the data should improve.

Together, these two rules define Barry's character: he is not a chatbot that asks everything upfront, nor a database that stores everything silently. He is an intelligence agent who acquires the minimum information needed to act, tracks what he knows and doesn't know, and gets smarter with every interaction.

3. The Four Intelligence Scopes

Every piece of intelligence belongs to exactly one scope. The scope determines who owns it, who can see it, how long it lives, and how it moves between surfaces.

Workspace — Shared business truth

Intelligence about the business itself. Should eventually be shared across all users of the same organization. Durable — changes slowly, usually by deliberate human decision.

  • Examples from the current codebase:
  • ICP / target market definition — currently stored at users/{uid}/icpProfiles, companyProfile/current, and RECON sections in dashboards/{uid} (three locations, no reconciliation)
  • Value proposition — stored at dashboards/{uid}.valueProposition, collected during onboarding Step 3 and RECON Section 1
  • Competitive landscape — RECON Section 8, stored in dashboards/{uid}
  • Product/service description — extracted by analyze-website, stored in RECON Section 2
  • Target industries, company sizes, geographies — RECON Section 3
  • Excluded industries — dashboards/{uid}.excludedIndustries (note: this is actually temporary strategy, not durable truth — a scope error in the current system)

Key characteristic: Workspace intelligence is about "what is our business" and "who are our customers." It is true regardless of which user is logged in, which contact they're engaging, or what objective they're pursuing right now.

User — Individual context

Intelligence about the specific person using IDYNIFY. Personal to them, not shared with other users of the same business.

  • Examples from the current codebase:
  • Communication style preferences — RECON Section 9 (Messaging), stored in dashboards/{uid}
  • Aggregate strategy stats — users/{uid}/barry_memory.strategy_stats, written by barryOutcomeAttribution.js
  • Gmail connection state — users/{uid}/integrations/gmail
  • Subscription tier and credits — users/{uid}.subscriptionTier, credits
  • Onboarding progress — users/{uid}.onboarding.* flags

Key characteristic: User intelligence is about "how this person works" and "what this person prefers." Two salespeople at the same company have different communication styles, different relationship networks, and different strategy outcomes.

Relationship — Person/company specific

Intelligence about a specific contact, company, or the user's relationship with them. Evolves continuously through interactions.

  • Examples from the current codebase:
  • Per-contact Barry memory — users/{uid}/contacts/{cid}.barry_memory (what_worked, what_didnt_work, channels_tried, preferences, new_facts), written by barryMemoryService.js
  • Relationship warmth — warmth_level with relationship_state_source tracking (user_set vs barry_inferred), inferred by inferRelationshipWarmth.js
  • Contact identity — name, title, company, email, resolved by contactIdentityService.js with 6-step hierarchy and CANONICAL_FIELDS protection
  • Engagement history — session outcomes, channels used, NBS derivation
  • Brigade assignment and transition history — users/{uid}/contacts/{cid}.brigade, immutable transition log
  • Company ICP fit score — calculated by icpScoring.js against the active ICP profile

Key characteristic: Relationship intelligence is about "what we know about this person/company" and "how our interactions with them have gone." It is cumulative — every session adds to it — and it is the primary input to message generation and strategy recommendation.

Mission — Temporary objective

Intelligence about what the user is trying to accomplish right now. Expected to change frequently. Scoped to a specific objective, campaign, or engagement goal.

  • Examples from the current codebase:
  • Mission objectives — users/{uid}/missions/{mid}.outcome_goal, per-contact engagement plans
  • Engagement intent — selected per-contact in Hunter (e.g., "Schedule meeting", "Get referral"), ephemeral per-session
  • Campaign goals — cadence targets, send counts, reply rate objectives
  • "This quarter's focus" — currently stored identically to permanent business truth (e.g., idealCustomerTypes in dashboards/{uid}), a scope error

Key characteristic: Mission intelligence is about "what are we trying to do right now." It has an expected end — the mission completes, the campaign finishes, the quarter changes. Intelligence that outlives its mission should be promoted to a more durable scope (Relationship or Workspace) or archived.

Note on the current codebase: No explicit workspace or mission entity exists today. All business intelligence is stored under user-scoped paths. Mission intelligence is fragmented across per-contact fields and per-session state. The four scopes describe the target architecture's conceptual model, not today's storage.

4. The Twelve Dimensions

Every intelligence object must express these twelve dimensions. An intelligence object missing any dimension is incomplete — it can still be stored and used, but the system should know what's missing and seek to fill it.

#DimensionQuestion It AnswersWhy It Matters
1 Subject / Scope Workspace / User / Relationship / Mission? Determines ownership, visibility, and lifetime. A value proposition is Workspace truth; a contact's preferred greeting is Relationship intelligence. Misscoping creates the bugs the audit found — temporary strategy stored as permanent truth, business facts locked to individual users.
2 Meaning What exactly does this fact represent? A field name like idealCustomerTypes is ambiguous. Is it "who we sell to" (descriptive) or "who we should target" (prescriptive)? Meaning makes the distinction explicit so Barry can use it correctly in prompts and decisions.
3 Source Where did Barry learn this? User assertion, website extraction, Gmail analysis, Apollo enrichment, Barry inference from behavior, outcome attribution, AI analysis. The source determines baseline trustworthiness and whether the value can be overwritten.
4 Evidence What observations support this? "Sarah prefers email" is stronger when backed by "3 email replies, 0 phone pickups, user confirmed" than when backed by "default assumption." Evidence lets Barry explain his reasoning and lets the user correct it.
5 Authority Which source can override another? Today, only inferRelationshipWarmth.js implements this: if relationship_state_source === 'user_set', Barry creates a suggestion instead of overwriting. This pattern needs to generalize — user assertions should generally beat AI inferences, which should generally beat third-party enrichment, but domain-specific rules may vary.
6 Confidence Known / inferred / estimated — how certain? A user-typed value is known. A warmth level derived from 10 interactions is high-confidence inferred. An ICP match score from a single data point is low-confidence estimated. Confidence determines how aggressively Barry should act on the intelligence and whether to seek confirmation.
7 Temporal scope Durable truth / evolving truth / temporary strategy / mission-only? "We sell SaaS" is durable. "Sarah is warm" evolves. "This quarter we target Utah nonprofits" is temporary. "Get a meeting with the CFO" is mission-only. The temporal scope determines staleness rules, expiration behavior, and whether the intelligence should persist after its context ends.
8 Acquisition Discover / infer+confirm / ask / learn later? Follows Barry's Question Rule. Each intelligence object has a preferred acquisition method. Company size is discoverable (don't ask). Communication style is inferable from editing patterns (confirm if high-stakes). Budget authority must be asked. Org chart details can be learned later.
9 Consumer Which surfaces and decisions use this? Intelligence with no consumer is dead storage. Today, engagement_timeline subcollections have no reader. RECON Section 3 (Target Market, weight 15) is excluded from the client-side context pipeline. The Consumer dimension forces the question: if nothing reads it, why collect it?
10 Update trigger What evidence can change this? Relationship warmth should update when engagement outcomes change. ICP fit should update when the user refines their target market. Value proposition should update when the website changes. Without explicit triggers, intelligence becomes stale silently.
11 Contradiction behavior Overwrite / defer to user / surface disagreement / request confirmation? When Apollo says "VP of Sales" and the user typed "Director of Sales", what happens? Today: CANONICAL_FIELDS silently protects the user's value. The warmth system does better: it creates a barry_warmth_suggestion so the disagreement is visible. The contract must define a default and allow per-category overrides.
12 Requiredness Required for current objective / useful later / optional? Determines acquisition urgency. If Barry needs the user's value proposition to draft a first outreach message, it's required now. If he could use their competitive landscape but can work without it, it's useful later. If their favorite sports team might help with small talk someday, it's optional. Requiredness is always relative to an objective, not absolute.

5. Concrete Examples: Twelve Dimensions Applied

Five intelligence objects from the current codebase, each traced through all twelve dimensions. These demonstrate how the contract applies in practice.

Example A: Relationship Warmth

The most complete intelligence implementation in the current system.

DimensionCurrent Implementation

6. ConfidenceImplicit in source type — no explicit confidence score, but user-set is treated as definitive, barry-inferred as revisable

12. RequirednessRequired for message generation (guardrail checks warmth before allowing cold outreach)

Assessment: Warmth is the most complete intelligence implementation. It satisfies 10 of 12 dimensions. Missing: explicit confidence scoring (dimension 6 is implicit) and temporal staleness rules (dimension 7 has no expiration). This is the model to generalize.

Example B: Value Proposition

A Workspace fact treated as a User field.

DimensionCurrent Implementation
1. Subject/ScopeWorkspace (logically) but stored at dashboards/{uid}.valueProposition User-scoped
2. MeaningWhat makes this business different from competitors — the core differentiator
3. SourceUnknown. Could be: user-typed in onboarding Step 3 (field differentiator), AI-extracted by analyze-website, or manually edited in RECON Section 1. No provenance tracked
4. EvidenceNone stored. The value exists as a string with no supporting observations

Example C: Per-Contact Barry Memory (what_worked)

Cumulative learning from engagement sessions.

DimensionCurrent Implementation
1. Subject/ScopeRelationship — stored on users/{uid}/contacts/{cid}.barry_memory.what_worked
2. MeaningEngagement strategies, message styles, and approaches that produced positive outcomes with this specific contact
3. SourcebarryMemoryService.js writes after Barry engagement sessions. Source is always the outcome of a Barry-generated interaction
4. EvidenceImplicit in the session that generated it, but the evidence chain (which session, which message, which outcome) is not stored on the memory field itself
5. AuthorityBarry-only. User cannot directly edit barry_memory. No authority conflict because only one system writes

11. ContradictionAppend-only. New observations don't contradict old ones — they add to the history. If a strategy that once worked stops working, both facts coexist
12. RequirednessRequired for effective message generation — without it, Barry repeats failed strategies. The system correctly prioritizes it (P1 in assembler budget)

Assessment: Strong implementation. Satisfies dimensions 1–3, 5, 8, 10–12. Weak on 4 (evidence chain not preserved), 6 (confidence not distinguished), 7 (no temporal decay). Critical gap on 9: only reachable from the server-side assembler, invisible to Mission Control Barry where users actually chat.

These are the semantic categories of intelligence Barry needs to operate. They are defined by meaning, not by storage — a single Firestore document might contain intelligence from multiple categories, and a single category might be stored across multiple documents.

7. Architecture Principle

Architecture Principle

One intelligence contract does not mean one intelligence database.

Workspace, User, Relationship, and Mission intelligence may remain appropriately distributed across different Firestore collections, server-side caches, and client-side state. The contract defines how Barry requests and receives relevant intelligence — not where it lives.

A unified Barry context layer is the delivery mechanism, not a unified intelligence store. When Mission Control Barry needs to draft a message for Sarah, the context layer assembles: Workspace positioning (from wherever it's stored) + User messaging style (from wherever it's stored) + Relationship memory with Sarah (from wherever it's stored) + Mission objective (from wherever it's stored). The contract guarantees that each piece arrives with its provenance, confidence, and temporal scope intact.

This principle has three implications:

  1. Storage design follows the contract, not the other way around. We do not begin with "what Firestore collections do we need?" We begin with "what intelligence categories exist, what dimensions must each carry, and which surfaces consume them?" Storage is the answer to those questions, not a prior constraint.
  2. The context assembly layer is the unification point. Today's split-brain architecture (client-side barryContextStack.js for business breadth, server-side barryContextAssembler.js for relationship depth) is not a problem of storage — both systems read from appropriate stores. It is a problem of assembly: no surface calls both. The fix is a unified assembly function that knows which intelligence to gather for each surface, not a unified database.
  3. Migration is incremental. Existing stores do not need to be rewritten in one pass. Each intelligence category can be upgraded independently: add provenance tracking to RECON fields, add temporal scope to ICP profiles, add confidence to warmth inference. The contract defines the target; migration happens category by category as each area is touched.

  • Storage schema design or Firestore collection proposals
  • Context Requirements by Surface (which Barry surface needs which intelligence)
  • Onboarding experience design against the contract
  • Signal Bus / Action Executor integration
  • Specific confidence scoring algorithms or staleness decay functions
