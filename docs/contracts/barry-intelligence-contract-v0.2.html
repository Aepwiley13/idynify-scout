1. Definition of Barry Intelligence

Barry knows something when all of the following are true:

  1. He has a defined piece of intelligence about a known subject — not a raw data field, but a fact with meaning he can act on.
  2. He understands where it came from and how trustworthy it is — a user assertion, an AI inference, a third-party enrichment, or an observed behavior, each carrying different weight.
  3. He knows how long it should remain valid — a durable business truth, an evolving relationship state, a temporary strategy, or a mission-scoped objective.
  4. He knows what evidence may change it — which observations, outcomes, or user actions should trigger re-evaluation.
  5. He understands which decisions or objectives this intelligence can inform, even when it is not currently relevant to the active mission.

Intelligence that fails any of these conditions is incomplete. It may still be useful — raw data can become intelligence when the missing conditions are added — but Barry should not treat it with the same authority as intelligence that satisfies all five.

On dormant intelligence: Intelligence without a current consumer is only justified if the system understands what class of decisions or objectives it is intended to inform. A contact's alma mater might never matter — unless a mission objective involves university-alumni pathways. Dormant intelligence is legitimate when its decision class is defined. Speculative information with no known product purpose should not be collected.

The gap today: Most of IDYNIFY's stored data satisfies condition 1 (a defined fact) but fails conditions 2–5. RECON answers have no provenance (2), no temporal scope (3), no update triggers (4), and several sections never reach any Barry surface (5). The Intelligence Contract exists to close these gaps systematically.

2. The Intelligence Hierarchy

Not everything Barry encounters is intelligence. The system must distinguish four levels, because each level requires different handling.

Data

“Sarah replied yesterday.”

Raw observation or event. No interpretation, no scope.

→
Intelligence

“Sarah is an active relationship.”

Interpreted, scoped understanding derived from data or another source.

→
Actionable Intelligence

“Sarah is the strongest path to this objective.”

Intelligence relevant to the current decision or objective.

→
Decision

“Ask Sarah for an intro before cold outreach.”

Barry applies actionable intelligence and determines what to recommend or do.

Data is what happens. Intelligence is what it means. Actionable intelligence is what matters right now. Decision is what Barry does about it.

The contract governs the middle two levels. Data enters the system through producers (Gmail, Scout, engagement sessions, website analysis). Decisions are made by Barry's generation and recommendation surfaces. The contract defines how data becomes intelligence, how intelligence becomes actionable, and what properties each intelligence object must carry.

Why this matters: Today, the system collapses these levels. A RECON answer is stored as data but treated as intelligence. An ICP score is computed as actionable intelligence but carries no provenance from the underlying intelligence it was derived from. Scout swipe events are data that never becomes intelligence at all. Each level requires its own handling — a raw event does not need provenance tracking, but intelligence derived from it does.

3. Governing Rules

Three permanent product principles govern all intelligence operations. These are not guidelines — they are constraints that every future system must satisfy.

Barry's Question Rule

Discover what you can. Infer what you reasonably can. Confirm what matters. Ask only what you cannot know and need now. Learn everything else over time.

This rule establishes a priority order for intelligence acquisition. Barry's first instinct is never to ask the user — it is to discover (from websites, email, public data), then infer (from behavior, patterns, outcomes), then confirm (verify inferences that carry high consequence), and only then ask (when a decision requires information that cannot be discovered, inferred, or deferred). Everything that isn't immediately needed enters the "learn over time" path — Barry accumulates it passively from ongoing interactions.

Why this matters: Every question Barry asks is a withdrawal from the user's patience. The onboarding that asks 105 questions before delivering value violates this rule. The onboarding that analyzes a website, infers the business, confirms one critical assumption, and starts working — that follows it.

Barry's Intelligence Rule

Never collect intelligence without knowing who it belongs to, where it came from, how trustworthy it is, how long it should remain true, and what decisions it should improve.

This rule prevents the accumulation of unstructured data that no system reads. Today, engagement_timeline subcollections are written but never consumed. enrichment_provenance is tracked but never surfaced. Scout swipes are recorded with full context but produce zero learning. Each of these violates the Intelligence Rule: they collect without knowing what decisions the data should improve.

Barry's Evidence Rule

Barry's understanding should change because the evidence changed — not silently, arbitrarily, or merely because another value appeared.

Every meaningful change in Barry's understanding should eventually be explainable. Barry should be able to answer: What changed? Why did my understanding change? What evidence caused it? A warmth level that silently flips from "warm" to "cold" without a traceable cause violates this rule. A value proposition that is overwritten by a website re-crawl without recording that the previous version was user-confirmed violates this rule.

Together, these three rules define Barry's character: he is not a chatbot that asks everything upfront, nor a database that stores everything silently. He is an intelligence agent who acquires the minimum information needed to act, tracks what he knows and doesn't know, gets smarter with every interaction, and can explain why his understanding changed.

4. The Four Intelligence Scopes

Every intelligence object has one primary subject/scope. Related intelligence may exist at other scopes and be composed at decision time.

The four scopes remain Workspace, User, Relationship, and Mission. A single intelligence object does not span scopes. Instead, conceptually distinct scoped intelligence is composed by Barry when making a decision.

Workspace — Shared business truth

Intelligence about the business itself. Should eventually be shared across all users of the same organization. Durable — changes slowly, usually by deliberate human decision.

  • ICP / target market definition, value proposition, competitive landscape
  • Product/service description, pricing model
  • Target industries, company sizes, geographies
  • Brand voice and positioning — how the organization communicates and presents itself

Key characteristic: Workspace intelligence is about "what is our business" and "who are our customers." It is true regardless of which user is logged in, which contact they're engaging, or what objective they're pursuing right now.

User — Individual context

Intelligence about the specific person using IDYNIFY. Personal to them, not shared with other users of the same business.

  • Aggregate strategy stats, subscription tier, onboarding progress
  • Gmail connection state, integration preferences
  • Personal communication style — how this particular user naturally communicates, their formality level, editing patterns, tone preferences
  • Permissions — what Barry may do autonomously vs. what requires approval

Key characteristic: User intelligence is about "how this person works" and "what this person prefers." Two salespeople at the same company have different communication styles, different relationship networks, and different strategy outcomes.

Relationship — Entity and relationship-specific intelligence

Intelligence about a specific contact, company, or the user's relationship with them. Evolves continuously through interactions. This scope contains two conceptually distinct types of intelligence.

Entity Intelligence

Facts about who the person or company is.

Answers: “Who is Sarah?”

  • Name, title, company, role, seniority
  • Industry, geography, organization attributes
  • Contact identity resolved by contactIdentityService.js
  • Company ICP fit score
  • Contact-specific communication preferences — how this person tends to respond or prefers to engage

Relationship-Edge Intelligence

Facts about the connection between the user/workspace and that entity.

Answers: “Who is Sarah to me?”

  • Relationship strength/warmth, trust level
  • Communication and engagement history
  • What worked, what didn't, channels tried
  • Introductions and referrals made
  • Last meaningful interaction
  • Access/pathway the relationship creates

Both remain under Relationship scope for v0.2. The distinction is foundational for future relationship pathfinding — IDYNIFY should eventually be able to answer: "Who in my world gives me the strongest path toward this objective?" That requires relationship edges, not merely contact records.

Mission — Temporary objective

Intelligence about what the user is trying to accomplish right now. Expected to change frequently. Scoped to a specific objective, campaign, or engagement goal.

  • Mission objectives, engagement intent, campaign goals
  • Current ask, objective, and context — what the user is trying to accomplish in this interaction
  • "This quarter's focus" — temporary targeting strategy

Key characteristic: Mission intelligence is about "what are we trying to do right now." It has an expected end — the mission completes, the campaign finishes, the quarter changes. Intelligence that outlives its mission should be promoted to a more durable scope (Relationship or Workspace) or archived.

Composition at Decision Time

"How Barry should communicate" is not one intelligence object. It is composed from distinct scoped intelligence at decision time:

Workspace brand voice × User personal style × Relationship contact preferences × Mission current objective

→ appropriate communication for this specific situation

This composition model replaces a single generic "Messaging" category. Each component has its own provenance, its own update triggers, its own temporal scope. The brand voice rarely changes; the contact's preferences evolve with every interaction; the mission objective expires when the objective is met. Composing them produces context-appropriate communication without collapsing distinct intelligence into a single undifferentiated field.

Note on the current codebase: No explicit workspace or mission entity exists today. All business intelligence is stored under user-scoped paths. Mission intelligence is fragmented across per-contact fields and per-session state. Communication style is a single User-scoped field (RECON Section 9) that conflates brand voice, personal style, and contact preferences. The four scopes and the composition model describe the target conceptual model, not today's storage.

5. The Thirteen Dimensions

Every intelligence object must express these thirteen dimensions. An intelligence object missing any dimension is incomplete — it can still be stored and used, but the system should know what's missing and seek to fill it.

#DimensionQuestion It AnswersWhy It Matters
1 Subject / Scope Workspace / User / Relationship / Mission? Determines ownership, visibility, and lifetime. A value proposition is Workspace truth; a contact's preferred greeting is Relationship intelligence. Misscoping creates the bugs the audit found — temporary strategy stored as permanent truth, business facts locked to individual users.
2 Meaning What exactly does this fact represent? A field name like idealCustomerTypes is ambiguous. Is it "who we sell to" (descriptive) or "who we should target" (prescriptive)? Meaning makes the distinction explicit so Barry can use it correctly in prompts and decisions.
3 Source Where did Barry learn this? User assertion, website extraction, Gmail analysis, Apollo enrichment, Barry inference from behavior, outcome attribution, AI analysis. The source establishes provenance and determines baseline trustworthiness.
4 Evidence What observations support this? "Sarah prefers email" is stronger when backed by "3 email replies, 0 phone pickups, user confirmed" than when backed by "default assumption." Evidence lets Barry explain his reasoning and lets the user correct it.
5 Authority Which source can override another? Authority defines whose word takes precedence when sources disagree. User assertions generally override AI inferences, which generally override third-party enrichment — but domain-specific rules may vary. Authority is independent of confidence: a user's input may have high authority (it takes precedence) without being objectively certain.
6 Confidence How strongly does available evidence support this? Confidence measures evidential support, not source authority. A user assertion starts with high confidence unless contradicted by observed outcomes or marked stale by temporal rules. An inference backed by ten observations has higher confidence than one backed by a single signal. Confidence changes as evidence accumulates or decays — authority does not.
7 Temporal scope Durable truth / evolving truth / temporary strategy / mission-only? "We sell SaaS" is durable. "Sarah is warm" evolves. "This quarter we target Utah nonprofits" is temporary. "Get a meeting with the CFO" is mission-only. The temporal scope determines staleness rules, expiration behavior, and whether the intelligence should persist after its context ends.
8 Acquisition Discover / infer+confirm / ask / learn later? Follows Barry's Question Rule. Each intelligence object has a preferred acquisition method. Company size is discoverable (don't ask). Communication style is inferable from editing patterns (confirm if high-stakes). Budget authority must be asked. Org chart details can be learned later.
9 Consumer / Decision Class Which surfaces and decisions use this — or could? Intelligence with no consumer is dead storage unless its decision class is defined. Today, engagement_timeline subcollections have no reader. RECON Section 3 (Target Market, weight 15) is excluded from the client-side context pipeline. The Consumer dimension forces the question: if nothing reads it now, what class of decisions would it inform?
10 Update trigger What evidence can change this? Relationship warmth should update when engagement outcomes change. ICP fit should update when the user refines their target market. Value proposition should update when the website changes. Without explicit triggers, intelligence becomes stale silently.
11 Contradiction behavior Overwrite / defer to user / surface disagreement / request confirmation? When Apollo says "VP of Sales" and the user typed "Director of Sales", what happens? Today: CANONICAL_FIELDS silently protects the user's value. The warmth system does better: it creates a barry_warmth_suggestion so the disagreement is visible. The contract must define a default and allow per-category overrides.
12 Requiredness Required for current objective / useful later / optional? Determines acquisition urgency. If Barry needs the user's value proposition to draft a first outreach message, it's required now. If he could use their competitive landscape but can work without it, it's useful later. Requiredness is always relative to an objective, not absolute.
13 Intelligence Status Where does this intelligence sit in its lifecycle? Status tracks how intelligence was established, whether it remains reliable, and whether it has been superseded. It is the lifecycle dimension — separate from confidence (how strongly evidence supports it) and authority (whose word takes precedence). See Section 6 for the full status model.

6. Intelligence Status and Lifecycle

Intelligence Status (dimension 13) tracks where a piece of intelligence sits in its lifecycle. These are conceptual states — they define the semantics Barry needs to reason about his own knowledge.

StatusMeaningExample
Unknown Barry has no meaningful value yet A new contact with no communication history — warmth is unknown, not cold
Inferred Barry derived this from available signals Warmth set to "warm" by inferRelationshipWarmth.js based on Gmail import
Confirmed User or authoritative source verified it User manually sets warmth to "hot" in the contact profile
Observed Barry learned or validated this through behavior/outcomes what_worked memory entry written after a successful engagement session
Contested Credible sources disagree Barry infers "cold" but user previously set "warm" — a barry_warmth_suggestion is created
Stale Intelligence exists but may no longer be reliable Value proposition last updated 8 months ago; website has since changed
Superseded Newer or higher-authority intelligence replaced it User updates their ICP profile — the previous version is superseded, not deleted
Archived Deliberately retired from active intelligence A completed mission's objectives — still valuable history, no longer active

Status Is Not Confidence

Status and confidence are independent dimensions that answer different questions.

StatusConfidenceWhat It Means
InferredHigh (91%)Barry derived this from strong signals but no human has verified it
ConfirmedModerate (75%)User verified it, but the evidence base is thin or the assertion may be approximate
StaleFormerly highWas well-supported, but temporal rules suggest re-evaluation
ObservedHighValidated through real outcomes — strongest evidential basis
ContestedSplitMultiple credible signals disagree — confidence is undefined until resolved

On authority and confidence: "Our average deal size is $50,000" — said by a user — has high authority (user assertion takes precedence). But it may be exact, approximate, outdated, or contradicted by observed outcomes. Authority means Barry respects it as the governing value. Confidence reflects how well available evidence supports the underlying truth. Barry should eventually be capable of respecting authoritative human input while recognizing evidence that suggests the underlying truth may have changed.

Status Transitions Must Be Evidence-Driven

Governing Principle

Barry should not change the lifecycle status of intelligence without a reason that can be traced to evidence, user confirmation, an explicit freshness rule, or a higher-authority source.

Barry's beliefs do not silently change. Every meaningful transition should eventually be explainable.

TransitionRequires
Unknown → InferredAvailable signals that Barry can interpret — e.g., Gmail import reveals communication history
Inferred → ConfirmedUser confirmation or another authoritative validation
Confirmed → StaleAn applicable freshness/temporal rule or evidence that conditions may have changed
Confirmed → ContestedCredible contradictory evidence from a different source
Contested → SupersededSufficient evidence, user resolution, or a higher-authority/newer source
Observed → updated valueTraceable behavioral or outcome evidence
Any → ArchivedDeliberate retirement — mission completion, user action, or system cleanup rule
Design Intent

These transitions are not yet a finalized state machine. They establish the principle that status changes are traceable. The goal: Barry should eventually be able to explain what changed, why his understanding changed, and what evidence caused it.

Personal Style (User) defines how the individual communicates. Contact Preferences (Relationship) defines how the contact prefers to be engaged. Objectives (Mission) defines what the current ask is. Barry composes these at decision time rather than storing them as a single undifferentiated "messaging" field.

9. Architecture Principle

Architecture Principle

One intelligence contract does not mean one intelligence database.

Workspace, User, Relationship, and Mission intelligence may remain appropriately distributed across different Firestore collections, server-side caches, and client-side state. The contract defines how Barry requests, interprets, evaluates, composes, and receives relevant intelligence — not where it lives.

A unified Barry context layer is the delivery mechanism, not a unified intelligence store. When Mission Control Barry needs to draft a message for Sarah, the context layer assembles: Workspace positioning (from wherever it's stored) + User messaging style (from wherever it's stored) + Relationship memory with Sarah (from wherever it's stored) + Mission objective (from wherever it's stored). The contract guarantees that each piece arrives with its provenance, confidence, temporal scope, and lifecycle status intact.

This principle has three implications:

  1. Storage design follows the contract, not the other way around. We do not begin with "what Firestore collections do we need?" We begin with "what intelligence categories exist, what dimensions must each carry, and which surfaces consume them?" Storage is the answer to those questions, not a prior constraint.
  2. The context assembly layer is the unification point. Today's split-brain architecture (client-side barryContextStack.js for business breadth, server-side barryContextAssembler.js for relationship depth) is not a problem of storage — both systems read from appropriate stores. It is a problem of assembly: no surface calls both. The fix is a unified assembly function that knows which intelligence to gather for each surface, not a unified database.
  3. Migration is incremental. Existing stores do not need to be rewritten in one pass. Each intelligence category can be upgraded independently: add provenance tracking to RECON fields, add temporal scope to ICP profiles, add confidence to warmth inference, add status lifecycle to engagement objectives. The contract defines the target; migration happens category by category as each area is touched.

What v0.2 Does Not Cover (Deferred)

  • Context Requirements by Surface (which Barry surface needs which intelligence)
  • Existing Intelligence Producers inventory
  • Mapping the 105 RECON questions to intelligence categories and dimensions
  • Storage schema design or Firestore collection proposals
  • Onboarding experience design against the contract
  • Unified Barry Context implementation
  • Specific confidence scoring algorithms or staleness decay functions
  • Finalized status state machine or database enums
