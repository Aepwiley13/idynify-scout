1. Definition of Barry Intelligence

Barry knows something when all of the following are true:

  1. He has a defined piece of intelligence about a known subject — not a raw data field, but a fact with meaning he can act on.
  2. He understands where it came from and how trustworthy it is — a user assertion, an AI inference, a third-party enrichment, or an observed behavior, each carrying different weight.
  3. He knows how long it should remain valid — a durable business truth, an evolving relationship state, a temporary strategy, or a mission-scoped objective.
  4. He knows what evidence may change it — which observations, outcomes, or user actions should trigger re-evaluation.
  5. He understands which decisions or objectives this intelligence can inform, even when it is not currently relevant to the active mission.

Intelligence that fails any of these conditions is incomplete. It may still be useful — raw data can become intelligence when the missing conditions are added — but Barry should not treat it with the same authority as intelligence that satisfies all five.

Reachability Standard (Permanent)

A capability is not considered implemented, working, or currently available to Barry unless it traces a reachable Producer → Store/derived object → Consumer → Decision path. An orphan producer that writes data no consumer reads, or an intelligence object that never reaches a Barry surface, is not "available" even if the code exists. Any claim about what Barry "knows" or "can do" must cite this path or be marked as aspirational.

On dormant intelligence: Intelligence without a current consumer is only justified if the system understands what class of decisions or objectives it is intended to inform. A contact's alma mater might never matter — unless a mission objective involves university-alumni pathways. Dormant intelligence is legitimate when its decision class is defined. Speculative information with no known product purpose should not be collected.

The gap today: Most of IDYNIFY's stored data satisfies condition 1 (a defined fact) but fails conditions 2–5. RECON answers have no provenance (2), no temporal scope (3), no update triggers (4), and several sections never reach any Barry surface (5). The Intelligence Contract exists to close these gaps systematically.

2. The Intelligence Hierarchy

Not everything Barry encounters is intelligence. The system must distinguish these levels, because each requires different handling.

Data

“Sarah replied yesterday.”

Raw observation or event. No interpretation, no scope.

→
Intelligence

“Sarah is an active relationship.”

Interpreted, scoped understanding derived from data or another source.

→
Derived Intelligence

“Sarah is the strongest path to Acme.”

Computed from two or more intelligence objects. The inputs are its provenance.

→
Decision

“Ask Sarah for an intro before cold outreach.”

Barry applies intelligence and determines what to recommend or do.

C6 — v0.3 change
Derived Intelligence is now a named type at level 2 of the hierarchy. v0.2 called this level "Actionable Intelligence" — a misnomer that conflated the type of intelligence (derived from composition of other intelligence) with a relation to a decision context. "Actionable" is not a type of intelligence; it is a relation between any intelligence (including derived intelligence) and an active decision or objective. An ICP fit score is derived intelligence: it composes entity attributes, workspace ICP definition, and scoring weights. It becomes actionable when a decision (e.g., "which companies to surface next") requires it. The same fit score is not actionable during an unrelated cadence-editing session.

Data is what happens. Intelligence is what it means. Derived intelligence is what two or more intelligence objects mean together. Decision is what Barry does about it.

The contract governs the middle two levels. Data enters the system through producers (Gmail, Scout, engagement sessions, website analysis). Decisions are made by Barry's generation and recommendation surfaces. The contract defines how data becomes intelligence, how intelligence composes into derived intelligence, and what properties each intelligence object must carry.

3. Governing Rules and Scout Invariants

Three permanent product principles govern all intelligence operations, followed by four Scout-specific invariants that constrain all onboarding and search behavior.

Governing Rules

Barry's Question Rule

Discover what you can. Infer what you reasonably can. Confirm what matters. Ask only what you cannot know and need now. Learn everything else over time.

This rule establishes a priority order for intelligence acquisition. Barry's first instinct is never to ask the user — it is to discover (from websites, email, public data), then infer (from behavior, patterns, outcomes), then confirm (verify inferences that carry high consequence), and only then ask (when a decision requires information that cannot be discovered, inferred, or deferred). Everything that isn't immediately needed enters the "learn over time" path — Barry accumulates it passively from ongoing interactions.

Barry's Intelligence Rule

Never collect intelligence without knowing who it belongs to, where it came from, how trustworthy it is, how long it should remain true, and what decisions it should improve.

This rule prevents the accumulation of unstructured data that no system reads. Today, enrichment_provenance is surfaced in the EnrichmentPanel UI but not consumed by any Barry context assembler — Barry never sees it. Scout swipes produce narrow, ephemeral learning: savedIndustries feeds adaptive search signals to the next search-companies call via triggerAdaptiveSearch, and loadSwipeFeedback injects swipe patterns into the Mission Control chat prompt. But this learning is ephemeral — per-batch, per-surface, never accumulated into persistent cross-session intelligence. Each of these partially violates the Intelligence Rule: the data is collected but never graduates to durable intelligence with tracked provenance.

C1 — v0.3 evidence correction
v0.2 stated that enrichment_provenance was "tracked but never surfaced" and that scout swipes produced "zero learning." Both were incorrect. enrichment_provenance is surfaced in EnrichmentPanel.jsx:78-226 (source badges, field-to-source mapping). Scout swipes produce two narrow learning paths: DailyLeads.jsx:1779-1838 extracts savedIndustries from accepted companies and passes them as adaptiveSignals to search-companies.js:691-692, adjusting the next Apollo query; barryMissionChat.js:163-1161 loads the last 50 accepted/20 rejected companies and injects feedback into the Mission Control chat prompt. What remains true: neither path produces durable, cross-session intelligence. The swipe signals are ephemeral (extracted per batch, used once, discarded) and the prompt injection only reaches Mission Control Barry.
Barry's Evidence Rule

Barry's understanding should change because the evidence changed — not silently, arbitrarily, or merely because another value appeared.

Every meaningful change in Barry's understanding should eventually be explainable. Barry should be able to answer: What changed? Why did my understanding change? What evidence caused it? A warmth level that silently flips from "warm" to "cold" without a traceable cause violates this rule. A value proposition that is overwritten by a website re-crawl without recording that the previous version was user-confirmed violates this rule.

Together, these three rules define Barry's character: he is not a chatbot that asks everything upfront, nor a database that stores everything silently. He is an intelligence agent who acquires the minimum information needed to act, tracks what he knows and doesn't know, gets smarter with every interaction, and can explain why his understanding changed.

Scout Invariants

These four product rules are not aspirational — they constrain all onboarding and search behavior today and in every future version.

Scout Invariant 1 — One ICP Truth

There must be exactly one canonical ICP representation that every consumer reads. Any surface that writes ICP data must project it to that canonical location. Today this is companyProfile/current. Adding new ICP input surfaces does not mean adding new ICP storage locations.

Scout Invariant 2 — Search Must Have Targeting

search-companies must never be called with an empty companyProfile. The caller is responsible for assembling targeting data from whatever sources it has (website analysis, smart questions, existing ICP) and projecting it to the expected format before triggering the search.

Scout Invariant 3 — No Silent Dead Ends

Every user-facing state transition must lead to an actionable next state. A READY state with zero results must offer retry or ICP refinement — not an invisible CTA and a dead screen. An ERROR state must be recoverable.

Scout Invariant 4 — Dashboard Before Intelligence Write

Any function that writes intelligence to dashboards/{uid} must ensure the document exists before writing. initializeDashboard is the gate; no caller may skip it. Today analyze-website silently discards extracted data when no dashboard doc exists (analyze-website.js:379) — this is a data loss path that Invariant 4 prohibits.

4. Intelligence Scopes

Every intelligence object has one primary subject/scope. Related intelligence may exist at other scopes and be composed at decision time.

C10 — v0.3 change: Five scopes
v0.2 grouped Entity and Relationship-Edge under a single "Relationship" scope, noting the distinction was "foundational for future pathfinding." After stress-testing against the codebase, v0.3 separates them. The evidence: detectMutualIntroOpportunities in referralIntelligenceService.js:680-715 pairs two network contacts (networkContacts[i] and networkContacts[j]) for mutual introduction — the user is the broker, not a party to either entity. deriveIntroNbs at line 707 is called with contactName: aName, introTargetName: bName. This operates on Entity intelligence (who each person is) that is independent of the user's relationship to either. contactIdentityService.js resolves contact identity by merging across sources — again, Entity operations that are user-independent. Keeping them collapsed under one scope would force every Entity operation to carry a user key it does not need. The five scopes are: Workspace, User, Entity, Relationship, Mission.

Workspace — Shared business truth

Intelligence about the business itself. Should eventually be shared across all users of the same organization. Durable — changes slowly, usually by deliberate human decision.

  • ICP / target market definition, value proposition, competitive landscape
  • Product/service description, pricing model
  • Target industries, company sizes, geographies
  • Brand voice and positioning

Key characteristic: Workspace intelligence is about "what is our business" and "who are our customers." It is true regardless of which user is logged in, which contact they're engaging, or what objective they're pursuing.

User — Individual context

Intelligence about the specific person using IDYNIFY. Personal to them, not shared with other users of the same business.

  • Aggregate strategy stats, subscription tier, onboarding progress
  • Gmail connection state, integration preferences
  • Personal communication style — formality, editing patterns, tone
  • Permissions — what Barry may do autonomously vs. what requires approval

Key characteristic: User intelligence is about "how this person works." Two salespeople at the same company have different styles, networks, and outcomes.

Entity — Who someone or something is

Facts about a contact, company, or organization that are true regardless of any user's relationship to them.

  • Name, title, company, role, seniority
  • Industry, geography, organization attributes
  • Contact identity as resolved by contactIdentityService.js
  • Company enrichment data (Apollo, Google Places)

Why Entity is separate: "Sarah is VP of Engineering at Acme" is true regardless of which user in the workspace knows Sarah. Today all entity data is stored under users/{uid}/contacts/{cid}, coupling entity facts to a specific user. This means two users who both know Sarah store duplicate entity data with no reconciliation. Separating Entity from Relationship at the conceptual level allows future deduplication without requiring an immediate storage migration. The scope separation is a semantic commitment, not a storage commitment.

C5 — v0.3 change: Arbitrary edge endpoints
Relationship edges are not restricted to user-as-endpoint. Evidence: detectMutualIntroOpportunities pairs two contacts (networkContacts[i] and networkContacts[j]) where the user is the broker. deriveIntroNbs connects contactName to introTargetName — two entities with a potential edge that the user mediates but does not occupy. The model must accommodate edges between two arbitrary Entity nodes. This is the foundation for relationship pathfinding: "Who in my network gives me the strongest path to this target?"

Relationship — Connection between entities

Intelligence about the connection between two entities, or between the user and an entity. Evolves continuously through interactions.

  • Relationship strength/warmth, trust level
  • Communication and engagement history
  • What has worked, what hasn't, channels tried
  • Introductions and referrals made or possible
  • Last meaningful interaction
  • Access/pathway the relationship creates

Key characteristic: A Relationship edge connects two endpoints (Entity nodes or User — not necessarily with the user as one endpoint). Relationship intelligence answers "what is the connection between A and B?" and can be traversed for pathfinding. An edge from User→Sarah, an edge from Sarah→CFO at Acme, and the user's intent to reach that CFO together compose a path.

Mission — Temporary objective

Intelligence about what the user is trying to accomplish right now. Expected to change frequently. Scoped to a specific objective, campaign, or engagement goal.

  • Mission objectives, engagement intent, campaign goals
  • Current ask, objective, and context
  • "This quarter's focus" — temporary targeting strategy

Key characteristic: Mission intelligence has an expected end — the mission completes, the campaign finishes. Intelligence that outlives its mission should be promoted to a more durable scope (Entity, Relationship, or Workspace) or archived.

Composition at Decision Time

"How Barry should communicate" is not one intelligence object. It is composed from distinct scoped intelligence at decision time:

Workspace brand voice × User personal style × Entity who they are × Relationship how we connect × Mission current objective

→ appropriate communication for this specific situation

Each component has its own provenance, update triggers, and temporal scope. The brand voice rarely changes; the entity's identity evolves with career moves; the relationship history accumulates with every interaction; the mission objective expires when met. Composing them produces context-appropriate communication without collapsing distinct intelligence into a single field.

Note on the current codebase: No explicit workspace, entity, or mission entity exists today. All business intelligence is stored under user-scoped paths. Entity and relationship data are both on users/{uid}/contacts/{cid}. The five scopes describe the target conceptual model, not today's storage.

5. The Intelligence Dimensions

Every intelligence object must express these dimensions. An intelligence object missing any dimension is incomplete — it can still be stored and used, but the system should know what's missing and seek to fill it.

C2 — v0.3 structural change
v0.2 dimensions 9 (Consumer/Decision Class) and 12 (Requiredness) have been removed from the intelligence object. They were never properties of the intelligence itself — they were properties of the relationship between intelligence and a consuming decision. A contact's warmth level does not know or care which surfaces consume it. Instead, decisions declare their requirements: the guardrail decision requires warmth (with minimum confidence), the message-generation decision requires what_has_worked (P1 priority). This is the pull model: decisions pull the intelligence they need, with declared requirements and minimum-quality thresholds, rather than intelligence objects pushing themselves toward consumers they've been told about.
C4 — v0.3 structural change
v0.2 dimensions 5 (Authority) and 11 (Contradiction behavior) have been moved from per-object to source-level policy. Authority is not a property of the intelligence object; it is a property of the source type. User assertions take precedence over Barry inferences; inferences take precedence over third-party enrichment; observed outcomes carry the strongest evidential weight. These rules apply uniformly across all intelligence — defining them per-object would create a matrix of per-field override rules that no one could maintain. The source-level policy is defined once, in the system's Source Authority and Contradiction Policy.
#DimensionQuestion It AnswersWhy It Matters
1 Subject / Scope Workspace / User / Entity / Relationship / Mission? Determines ownership, visibility, and lifetime. A value proposition is Workspace truth; a contact's title is Entity intelligence; the warmth between you and that contact is Relationship intelligence. Misscoping creates the bugs the audit found — temporary strategy stored as permanent truth, business facts locked to individual users.
2 Meaning What exactly does this fact represent? A field name like idealCustomerTypes is ambiguous. Is it "who we sell to" (descriptive) or "who we should target" (prescriptive)? Meaning makes the distinction explicit.
3 Source Where did Barry learn this? User assertion, website extraction, Gmail analysis, Apollo enrichment, Barry inference from behavior, outcome attribution, AI analysis. Source establishes provenance and determines baseline trustworthiness. Source-level authority and contradiction policies apply (see below).
4 Evidence What observations support this? "Sarah prefers email" is stronger when backed by "3 email replies, 0 phone pickups, user confirmed" than "default assumption." Evidence lets Barry explain reasoning and lets the user correct it.
5 Confidence How strongly does available evidence support this? Confidence measures evidential support, not source authority. A user assertion starts with high confidence unless contradicted. An inference backed by ten observations has higher confidence than one backed by a single signal. Confidence changes as evidence accumulates or decays.
6 Temporal Scope Durable truth / evolving truth / temporary strategy / mission-only? "We sell SaaS" is durable. "Sarah is warm" evolves. "This quarter target fintech" is temporary. "Get a meeting with the CFO" is mission-only. Temporal scope determines staleness rules and expiration behavior.
7 Acquisition Discover / infer+confirm / ask / learn later? Follows Barry's Question Rule. Company size is discoverable (don't ask). Communication style is inferable (confirm if high-stakes). Budget authority must be asked. Org chart can be learned later.
8 Update Trigger What evidence can change this? Warmth should update when engagement outcomes change. ICP fit should update when the user refines targeting. Value proposition should update when the website changes. Without explicit triggers, intelligence becomes stale silently.
9 Source Tier How was this intelligence established? Distinct from Source (dimension 3, which names the specific origin). Source Tier classifies the epistemological category: User Assertion, Observed Outcome, AI Inference, Third-Party Enrichment, System Default. See Section 6 for how Source Tier interacts with Operative Status.
10 Operative Status Active / Superseded / Archived? Is this the current governing value? Has it been replaced by a newer or higher-authority version? Or has it been deliberately retired? Operative status is the lifecycle state. Exactly one version of a given intelligence key is Active at any time; superseded versions are retained for history and audit.
11 Sensitivity / Visibility Who may see this intelligence? Internal-only (Barry's working data), user-visible (shown in UI), team-shared (visible to workspace members), or external-safe (can appear in outgoing communication). Today no intelligence carries visibility metadata — the UI decides per-component what to display. Making visibility a dimension means Barry can reason about what to surface and what to keep internal.
12 Identity / Stability How stable is the subject's identity? A contact may merge (two records are the same person), split (a record was conflated), or be corrected (wrong person). contactIdentityService.js handles merges today. A company may rename, be acquired, or split. Intelligence anchored to an unstable subject needs to survive identity changes. This dimension records whether the subject's identity has been verified, is provisional, or is in conflict.
13 Cardinality Scalar / set / time-series / bounded list? warmth_level is a scalar: one value at a time, overwritten in full. what_has_worked is a bounded list: append-only, capped at a maximum count. The timeline subcollection is a time-series: ordered events, never overwritten, queried by range. industries is a set: unordered, deduplicated. Cardinality determines valid write operations (overwrite vs. append vs. add-to-set), capacity rules (bounded list needs a cap), and query patterns (time-series needs range queries). Implicit today; making it explicit prevents the bug where an append-only field is silently overwritten.
C3 — v0.3 change: Splitting the old dimension 13
v0.2's single "Intelligence Status" dimension tried to carry too much. It conflated how the intelligence was established (Unknown/Inferred/Confirmed/Observed — really an evidence tier), whether it is currently operative (Active/Superseded/Archived), and orthogonal quality flags (Stale/Contested). These are independent axes. An intelligence object can be Active + Inferred + Stale (Barry inferred it, it's the current value, but the evidence is old). It can be Active + Confirmed + Contested (user confirmed it, it's the current value, but new evidence disagrees). Combining these into a single linear status creates impossible transitions — you can't be both Confirmed and Contested in a single enum. v0.3 splits them into: Source Tier (dimension 9), Operative Status (dimension 10), and orthogonal flags (Stale, Contested) that can be applied to any Active intelligence.

Source Authority and Contradiction Policy

C4 — v0.3 change
Authority and contradiction behavior are now source-level policies, not per-object dimensions. Defined once, applied everywhere.

When sources disagree, authority is resolved by source tier:

Source TierAuthority LevelContradiction Behavior
User Assertion Highest. The user's word takes precedence. If Barry disagrees, he surfaces a suggestion (the barry_warmth_suggestion pattern) rather than overwriting. User can accept or dismiss.
Observed Outcome High. Real-world results are strong evidence. If observed outcomes contradict a user assertion, the Contested flag is set. Barry should surface the contradiction and let the user decide.
AI Inference Medium. Barry's reasoning from available signals. Defers to User Assertion and Observed Outcome. Overwrites System Default and Third-Party Enrichment. May surface as suggestion when contradicting higher-authority sources.
Third-Party Enrichment Low-medium. External data (Apollo, Google Places). Today: CANONICAL_FIELDS in the enrichment pipeline silently protects user-set values. Third-party data fills gaps but does not override.
System Default Lowest. Assumed until evidence arrives. Overwritten by any higher source without recording the change.

The governing principle: When sources conflict, prefer the source with higher authority. When authority is equal, prefer the more recent source. When the contradiction is material to an active decision, surface the disagreement to the user rather than resolving silently.

6. Intelligence Status and Lifecycle

Intelligence status is now three independent axes, not a single linear state. Each axis answers a different question.

Axis 1: Source Tier

How was this intelligence established? Set when the intelligence is created or updated.

Source TierMeaningExample
User Assertion The user directly stated or confirmed this User sets warmth to "hot" in the contact profile; warmth_level_source: "user_set"
Observed Outcome Barry learned this from real interaction outcomes what_has_worked memory entry written by barryOutcomeAttribution.js:182 after a successful engagement
AI Inference Barry derived this from available signals Warmth set to "warm" based on Gmail import — tracked via warmth_level_source: "barry_inferred"
Third-Party Enrichment External data source provided this Apollo returns company size, industry, funding. Provenance tracked in enrichment_provenance
System Default No evidence yet; assumed until evidence arrives A new contact with no communication history — warmth is unknown (system default), not cold

Axis 2: Operative Status

Is this the current governing value?

StatusMeaningInvariant
Active This is the current value Barry should use Exactly one version of a given intelligence key is Active at any time
Superseded Replaced by a newer or higher-authority version Retained for history. User updates ICP — the previous version is superseded, not deleted
Archived Deliberately retired from active intelligence A completed mission's objectives — still valuable history, no longer active

Axis 3: Quality Flags (orthogonal)

Flags that can be applied to any Active intelligence. They are not statuses in themselves — they modify the Active status.

FlagMeaningWhen SetWhen Cleared
Stale Intelligence exists but may no longer be reliable A temporal/freshness rule fires, or the subject's conditions have observably changed Re-confirmed, re-observed, or explicitly refreshed
Contested Credible sources disagree about this value A source with comparable or higher authority provides a contradictory value User resolves the contradiction, or sufficient evidence accumulates to resolve it

Combined examples:

  • Active + AI Inference + no flags = Barry inferred this, it's the current value, no issues
  • Active + User Assertion + Stale = User said this, it's the current value, but it's been a long time
  • Active + User Assertion + Contested = User said this, it's the current value, but Barry has contradictory evidence
  • Superseded + Observed Outcome = An older observation that has been replaced by a newer one

Status Transitions Must Be Evidence-Driven

Governing Principle

Barry should not change the operative status or quality flags of intelligence without a reason that can be traced to evidence, user confirmation, an explicit freshness rule, or a higher-authority source.

TransitionRequires
System Default → Active (any tier)Evidence arrives that establishes a value
Active → +Stale flagAn applicable temporal rule or evidence that conditions may have changed
Active → +Contested flagCredible contradictory evidence from a comparable-authority source
Active → SupersededA newer or higher-authority value takes its place
Active → ArchivedDeliberate retirement — mission completion, user action, or system cleanup rule
Stale flag → clearedRe-confirmation, re-observation, or explicit refresh
Contested flag → clearedUser resolution or sufficient evidence to resolve
Design Intent

These transitions are not yet a finalized state machine. They establish the principle that status changes are traceable. The goal: Barry should eventually be able to explain what changed, why his understanding changed, and what evidence caused it.

The Split-Brain Problem

No surface calls both barryContextStack (business breadth) and assembleBarryContext (relationship depth). This means:

  • Mission Control Barry knows the business, the ICP, and all 500 contacts — but not per-contact memory, strategy stats, or what has worked with specific people
  • Hunter Barry knows per-contact memory, warmth, and engagement history — but not the business's value proposition, ICP, or RECON data

This is not a storage problem — both systems can read from the same Firestore collections. It is an assembly problem: no unified assembly function knows which intelligence to gather for each decision surface.

RECON Section 3 gap: reconSectionMap.js:13-18 maps sections 1, 2, 4, 5, and 9. Section 3 (Target Market Firmographics, weight 15) is excluded. Mission Control Barry never receives target market data even though it is stored and editable by the user.

What barryMissionChat does NOT receive: Barry Mission Control sees a flat list of contacts (with relationship_state and strategic_value from barryContextStack.js:40-41) but NOT referral_data, warmth_level, graph edges, or any relationship network data. Barry Mission Control cannot answer "who in my network connects me to Acme?" because the graph data does not reach it.

10. Architecture Principle

Architecture Principle

One intelligence contract does not mean one intelligence database.

Workspace, User, Entity, Relationship, and Mission intelligence may remain distributed across different Firestore collections, server-side caches, and client-side state. The contract defines how Barry requests, interprets, evaluates, composes, and receives relevant intelligence — not where it lives.

A unified Barry context layer is the delivery mechanism, not a unified intelligence store. When Mission Control Barry needs to draft a message for Sarah, the context layer assembles: Workspace positioning + User messaging style + Entity identity (Sarah) + Relationship memory + Mission objective. The contract guarantees that each piece arrives with its provenance, confidence, temporal scope, and lifecycle status intact.

This principle has three implications:

  1. Storage design follows the contract, not the other way around. We do not begin with "what Firestore collections do we need?" We begin with "what intelligence categories exist, what dimensions must each carry, and which decisions consume them?" Storage is the answer to those questions, not a prior constraint.
  2. The context assembly layer is the unification point. Today's split-brain architecture (client-side barryContextStack.js for business breadth, server-side barryContextAssembler.js for relationship depth) is not a problem of storage. It is a problem of assembly: no surface calls both. The fix is a unified assembly function that knows which intelligence to gather for each decision surface, not a unified database.
  3. Migration is incremental. Existing stores do not need to be rewritten in one pass. Each intelligence category can be upgraded independently: add provenance tracking to RECON fields, add temporal scope to ICP profiles, add confidence to warmth inference, add status lifecycle to engagement objectives. The contract defines the target; migration happens category by category.

11. Still Open — Explicitly Not Decided

These questions are deferred because they depend on implementation experience, not because they are unimportant. Each is named here so that no future revision silently assumes an answer that was never given.

Open Question 1: Confidence Scoring Model

Should confidence be a continuous score (0–100), a tier (low/medium/high), or a structured evidence-count object? The choice affects storage, query patterns, and whether confidence can be compared across intelligence types. strategy_stats already uses a count threshold (total_attributions < 3 → null, >= 5 → activated in prompt). Is this the right pattern, or should explicit confidence scores be stored?

Open Question 2: Staleness Decay Functions

How should different temporal scopes decay? A value proposition last updated 8 months ago may still be accurate. A warmth assessment from 8 months ago is likely stale. Should decay be time-based (N days since last update), event-based (N interactions without re-evaluation), or signal-based (external evidence of change)? Should different intelligence categories have different decay rates?

Open Question 3: Entity Scope Storage

Separating Entity from Relationship at the conceptual level is decided (C10). Whether to separate them in storage is not. Today all entity data lives on users/{uid}/contacts/{cid}. A shared entities/{eid} collection would enable deduplication and workspace-wide entity intelligence, but requires contact identity reconciliation across users. This is a migration question, not a semantic one.

Open Question 4: Cross-Surface Context Assembly

Should there be one unified assembly function that serves all Barry surfaces, or should each surface declare its requirements and a resolver assembles the matching intelligence? The pull model (C2) favors the latter: each decision declares what it needs, and the resolver gathers intelligence from whatever stores contain it. But the implementation cost differs significantly — a per-surface declaration system is more flexible but harder to build and debug than a single function with surface-specific branches.

Open Question 5: Workspace Scope Activation

Today all business intelligence is stored under user-scoped paths. When does Workspace become a real scope with shared storage? This depends on multi-user support: a single-user product doesn't need workspace-level deduplication. The scope is defined now so the model doesn't need to be redesigned when multi-user arrives, but the storage migration is tied to a product decision, not a contract decision.

Open Question 6: Relationship Pathfinding Data Model

Relationship edges with arbitrary endpoints (C5) enable pathfinding: "Who in my network connects me to Target Corp?" But the data model for storing and querying graph edges in Firestore is not defined. Adjacency lists, edge collections, or an external graph store each have different query and scaling characteristics. This is an implementation decision deferred until the relationship graph feature is scoped.

Open Question 7: Sensitivity/Visibility Enforcement

Dimension 11 (Sensitivity/Visibility) defines the categories. How enforcement works is not decided. Should each component query a visibility attribute before rendering? Should the context assembler filter by visibility level before injecting into prompts? Should Barry have access to "internal" intelligence that users cannot see? These are UI/architecture decisions that interact with the permission model.
