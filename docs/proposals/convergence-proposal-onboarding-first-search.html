1. The Problem

OnboardingFlow writes four fields that buildApolloQuery never reads. Barry's onboarding intelligence does not reach the first Scout search.

Gap — Dormant Fields

OnboardingFlow produces idealCustomerTypes, excludedIndustries, valueProposition, perfectCustomer. These are free-text strings written to companyProfile/current.

Gap — Missing Fields

buildApolloQuery consumes industries[], companyKeywords[], companySizes[], locations[], isNationwide, searchStrategy. None of these are populated by OnboardingFlow.

Gap — Discarded Intelligence

analyze-website (Step 2) returns targetIndustry, targetCompanySize, icpSummary to the client. OnboardingFlow checks data.success !== false and discards the extraction. This structured intelligence never reaches the ICP or the search.

By contrast, BarryOnboarding.jsx:310-338 works because it produces the exact structured fields Apollo needs. The fix is not a UX redesign—it is a translation layer that converts the intelligence Barry already collects into the targeting structure Apollo requires.

2. Four Architecture Decisions

D1: ICP Identity Proposed

Decision

An ICP is a versioned document with a stable identifier. It contains structured targeting fields (what buildApolloQuery consumes), source intelligence (the raw inputs that produced those fields), and metadata. Multiple ICPs are supported through distinct document IDs.

Minimal schema for onboarding-generated ICP:

{
  "icpId": "primary",
  "version": 1,
  "source": "onboarding_flow",
  "createdAt": "2026-10-28T...",

  // Structured targeting — what buildApolloQuery reads
  "targeting": {
    "industries": ["healthcare", "medical devices"],
    "companyKeywords": ["hospital", "clinic", "health system"],
    "companySizes": ["51-200", "201-500"],
    "locations": ["Utah"],
    "isNationwide": false,
    "searchStrategy": "industry_only",
    "lookalikeSeed": null,
    "foundedAgeRange": null
  },

  // Raw intelligence — what produced the targeting
  "sourceIntelligence": {
    "websiteExtraction": {
      "targetIndustry": "Healthcare companies and hospital systems",
      "targetCompanySize": "mid-market",
      "icpSummary": "...",
      "confidence": 72
    },
    "smartQuestions": {
      "fastestClose": "Hospital systems with 50-500 beds",
      "avoidIndustries": "Government, K-12 education",
      "differentiator": "HIPAA-compliant patient engagement platform",
      "perfectCustomer": "Regional hospital network in the Mountain West"
    }
  },

  // Sufficiency assessment — did this pass the gate?
  "sufficiency": {
    "pass": true,
    "hasKeywords": true,
    "hasGeography": true,
    "checkedAt": "2026-10-28T..."
  }
}

D2: ICP Authority Proposed

Decision

The authoritative ICP lives at users/{uid}/icpProfiles/{icpId}. For the onboarding-generated ICP: users/{uid}/icpProfiles/primary.

companyProfile/current is not the source of truth. It is a legacy projection target. Onboarding writes to the authoritative store first, then projects a compatible view to companyProfile/current for existing consumers.

This separates authority from consumption without migrating existing readers. The six existing writers to companyProfile/current (BarryOnboarding, ICPSettings, updateIcpFromChat, setActiveIcpProfile, dashboardUtils, adminUpdateUserICP) continue to work unchanged—they will be migrated to write to icpProfiles in a future sprint.

D3: Projection Proposed

Decision

A pure function projectToLegacyProfile(icpDoc) maps the authoritative ICP into the companyProfile/current shape. It runs after every authoritative write during onboarding.

function projectToLegacyProfile(icp) {
  return {
    ...icp.targeting,
    source: icp.source,
    updatedAt: icp.createdAt,
    scoringWeights: DEFAULT_WEIGHTS,
    managedByBarry: true,
    barryConfidenceScore:
      (icp.sourceIntelligence?.websiteExtraction?.confidence ?? 50) / 100,
    // Preserve original intelligence for any consumer that reads it
    idealCustomerTypes:
      icp.sourceIntelligence?.smartQuestions?.fastestClose || '',
    excludedIndustries:
      icp.sourceIntelligence?.smartQuestions?.avoidIndustries || '',
    valueProposition:
      icp.sourceIntelligence?.smartQuestions?.differentiator || '',
    perfectCustomer:
      icp.sourceIntelligence?.smartQuestions?.perfectCustomer || '',
  };
}

search-companies continues to receive companyProfile in the request body, reading the same structured fields it always has. No change to the server function.

D4: First-Search Targeting Sufficiency Proposed

Decision

A search is targetable if and only if it has at least one keyword dimension and at least one geographic dimension. This is deterministic, testable, and enforced at two points: client-side before triggering search-companies, and server-side in search-companies before calling Apollo.

SUFFICIENT =
  ( industries.length > 0  OR  companyKeywords.length > 0 )
  AND
  ( locations.length > 0  OR  isNationwide === true )

Rationale from buildApolloQuery behavior:

  • Without keywords: Apollo has no q_organization_keyword_tags and returns untargeted results. The log already warns: "⚠️ No industries selected!"
  • Without geography: Apollo returns global results or nothing useful. The log warns: "⚠️ No locations selected and not nationwide!"
  • companySizes strengthens targeting but its absence doesn't make a search meaningless—it remains optional.

On failure, the ICP is written with sufficiency.pass = false and barryState is set to ERROR with a reason code, surfacing the problem rather than running a doomed search.

Change 1 — Capture Website Extraction

Change 2 — New Netlify Function: translate-icp

netlify/functions/translate-icp.js (new) — Takes combined onboarding intelligence. Returns structured ICP targeting fields. Uses a single Claude API call with a tightly constrained prompt that outputs the exact JSON shape buildApolloQuery requires.

// translate-icp input
{
  "websiteExtraction": {
    "targetIndustry": "Healthcare companies and hospital systems",
    "targetCompanySize": "mid-market",
    "icpSummary": "...",
    "whoTheyServeTo": "...",
    "confidence": 72
  },
  "smartQuestions": {
    "fastestClose": "Hospital systems with 50-500 beds",
    "avoidIndustries": "Government, K-12 education",
    "differentiator": "HIPAA-compliant patient engagement platform",
    "perfectCustomer": "Regional hospital network in the Mountain West"
  }
}

// translate-icp output
{
  "industries": ["healthcare", "medical devices", "hospitals"],
  "companyKeywords": ["hospital", "health system", "clinic", "patient"],
  "companySizes": ["51-200", "201-500"],
  "locations": ["Utah", "Idaho", "Wyoming", "Montana", "Colorado"],
  "isNationwide": false,
  "searchStrategy": "industry_only"
}

The prompt constrains Barry to output only the Apollo-compatible field shapes. Each field includes a brief explanation of why it was chosen, which becomes the observability trace (see §4).

Change 3 — Rewrite handleFinishQuestions

OnboardingFlow.jsx:423-493 — After collecting Step 3 answers:

  1. Call translate-icp with website extraction + smart question answers
  2. Check sufficiency gate (D4)
  3. Write authoritative ICP to icpProfiles/primary
  4. Project to companyProfile/current via projectToLegacyProfile()
  5. Set barryState: 'SEARCHING'
  6. Fire search-companies with projected profile
Change 4 — Server-Side Sufficiency Check

search-companies.js:~230 — Before entering the Apollo query path, validate the sufficiency rule against the received companyProfile. On failure: return early, set barryState: 'ERROR', log the specific missing dimensions.

4. Observability

The goal: inspect any first search and answer "Which pieces of onboarding intelligence caused this company to be searched for or returned?"

Translation Trace

The translate-icp function returns a reasoning object alongside the structured fields, linking each targeting decision to its source intelligence:

{
  "targeting": { "industries": ["healthcare", ...], ... },
  "reasoning": {
    "industries": {
      "derived_from": ["website.targetIndustry", "questions.fastestClose"],
      "rationale": "Website identifies healthcare as target industry;
                    fastest-close answer specifies hospital systems"
    },
    "locations": {
      "derived_from": ["questions.perfectCustomer"],
      "rationale": "Perfect customer answer specifies Mountain West region"
    },
    "companySizes": {
      "derived_from": ["website.targetCompanySize", "questions.fastestClose"],
      "rationale": "Website says mid-market; fastest-close says 50-500 beds
                    maps to 51-500 employees"
    }
  }
}

This reasoning is persisted on the ICP document. It does not need to reach Apollo—it is a diagnostic artifact for the team.

Query Trace

buildApolloQuery already logs which fields it consumes. We add a structured return alongside the Apollo query:

// In search-companies, after buildApolloQuery:
const queryTrace = {
  icpId: companyProfile.icpId || 'legacy',
  fieldsUsed: {
    industries: (companyProfile.industries || []).length > 0,
    companyKeywords: (companyProfile.companyKeywords || []).length > 0,
    companySizes: (companyProfile.companySizes || []).length > 0,
    locations: (companyProfile.locations || []).length > 0,
    isNationwide: !!companyProfile.isNationwide,
  },
  apolloParams: Object.keys(query),
  timestamp: new Date().toISOString()
};

This trace is written to the user doc alongside barryState: 'READY' so the dashboard can display it.

5. First-Search Targeting Sufficiency

The sufficiency rule is checked at two enforcement points:

Checkpoint Location On Failure
Client-side gate OnboardingFlow.jsx, after translate-icp returns Write ICP with sufficiency.pass = false. Set barryState: 'ERROR' with reason 'insufficient_targeting'. Do not call search-companies.
Server-side guard search-companies.js, before buildApolloQuery Return { success: false, error: 'insufficient_targeting' }. Set barryState: 'ERROR'. Log which dimensions were missing.

The server-side guard is the safety net. Even if a future client bypasses the gate, no untargeted search reaches Apollo.

Unresolved Decisions That Would Block Implementation

None. All four decisions required for this path are proposed above. No external dependency blocks the implementation.

One timing question to note: translate-icp adds a Claude API call between Step 3 completion and the search trigger. Expected latency: 2-4 seconds. The user is already in a waiting state (Step 4: Gmail or Step 5: Building List), so this latency is absorbed without UX impact. The netlify.toml timeout should be 30 seconds (generous, as the call is a single short-prompt completion).

8. Definition of Done

  • ☐ User completes OnboardingFlow → analyze-website extraction is captured (not discarded)
  • ☐ Smart question answers + website extraction sent to translate-icp
  • ☐ translate-icp returns structured targeting fields that buildApolloQuery can consume
  • ☐ Sufficiency gate prevents untargeted searches (deterministic, both client and server)
  • ☐ Authoritative ICP written to icpProfiles/primary with source intelligence + reasoning
  • ☐ Legacy projection written to companyProfile/current (existing consumers unaffected)
  • ☐ search-companies generates a meaningfully targeted Apollo query
  • ☐ Appropriate companies return for all four fixture personas
  • ☐ For any search: which onboarding intelligence caused which targeting field is inspectable
  • ☐ Vague-input fixture correctly fails the sufficiency gate

The test: Would the customer reasonably believe Barry understood who they wanted to target?
